# CEO Agent Service 安全与审核逻辑审查报告

审查日期：2026-08-25

范围：`app/audit_agent.py`、`app/agent_turn_runner.py`、`app/worker.py`、`app/store.py`，以及最近一周生产任务的只读状态。

## 结论

当前问题部分确实由安全/审核逻辑引起，但不是“安全校验太严格”这一单一问题，而是三种状态被混在同一条恢复链路中：

1. **普通、低风险、无已确认外部效果的消息/评审**；
2. **高风险或顺序敏感的外部动作**；
3. **外部效果未知的历史运行**。

三者都进入 `pending_reconciliation` 后，普通任务会长期等待外部证据，高风险任务又无法得到明确的人工决策，最终出现大量 `pending`、`processing` 和 `unknown`。

安全逻辑本身不应删除；应改成“按风险与效果状态分流”，并让每个分支有明确终态。

## 已确认发现

### 高危：未知效果与普通任务共用恢复状态

- 分类：权限控制 / 安全审计 / 备份恢复
- 证据：`app/audit_agent.py:188-312`、`app/worker.py:1779-1823`
- 现象：Audit unknown run 统一进入 reconciliation；普通消息、评审、提醒和付款审批没有在状态机层面分流。
- 影响：低风险任务会无限等待；高风险任务也没有清晰的人工决策入口。
- 整改：持久化 `risk_class`、`effect_state`、`recovery_policy` 三个正交字段，至少区分 `immutable_delivery`、`read_only_advice`、`high_risk_external_mutation`、`unknown_effect`。
- 验收：低风险且无回执的任务在新 generation 重跑；高风险任务进入 `needs_human` 并带具体选项；unknown 任务只能进入只读核对。

### 高危：`effect_started_count` 与真实外部效果混淆

- 分类：安全审计 / 接口安全
- 证据：`app/agent_turn_runner.py:926-951`、`app/agent_turn_runner.py:1000-1012`
- 现象：事件刚进入 `item.started` 就增加 effect 计数，之后本地授权合同校验失败仍会形成“已启动效果”的 unknown 记录。
- 影响：本地拒绝的动作被当成外部动作不明，导致普通任务长期 reconciliation。
- 整改：拆分为 `intent_started`、`authorization_passed`、`external_call_started`、`receipt_persisted`；只有 `external_call_started` 才能进入 unknown-effect 分支。
- 验收：授权合同校验失败且外部调用未开始时，旧 run 进入 `failed/no_effect`，任务自动换 generation；真实外部调用开始但无回执时，仍进入 unknown。

### 中危：恢复器对 processing unknown 的 lease 判断与任务状态耦合

- 分类：安全审计 / 备份恢复
- 证据：`app/worker.py:1783-1823`、`app/store.py:9652-9702`
- 现象：历史上没有有效 lease 的 processing unknown 也会被视为活跃任务；虽然已增加 stale recovery 修复，但状态转换仍分散在多个函数中。
- 影响：任务可能长时间停留在 processing，难以判断是正在执行还是孤儿任务。
- 整改：将 reconciliation lease 作为唯一租约；统一实现 `claim → reconcile → settle/requeue` 原子事务，并为 lease 过期提供单一入口。
- 验收：有效 lease 不被抢占；过期 lease 在一个周期内回到 pending reconciliation；任何 processing 状态都能找到有效 owner 或明确 recovery reason。

### 中危：普通 `needs_human` 缺少风险门槛

- 分类：权限控制 / 安全审计
- 证据：`app/worker.py:2260-2308`
- 现象：没有 decision options 时自动生成通用“重新核验/停止”选项，但没有根据风险判断是否真的需要人工。
- 影响：低风险不可变消息可能被错误升级为 needs_human；高风险动作的选项也可能过于笼统。
- 整改：`needs_human` 只能由风险策略生成；低风险任务不得返回 needs_human，高风险任务必须带动作、对象、风险、可选结果和取消后果。
- 验收：低风险任务没有人工卡片；高风险任务的每个选项可审计且不可直接绕过授权。

### 低危：审核工具表面过于分散

- 分类：安全审计 / 发布变更
- 证据：`app/agent_turn_runner.py:2213-2445`、`app/audit_agent.py:1100-1455`
- 现象：reviewed-read、reviewed-write、native CLI、Skill receipt 和 recovery authorization 分散在多个校验函数中。
- 影响：新增工具或新恢复路径容易遗漏其中一层校验，产生 `agent_cli_command_unreviewed`、`audit_recovery_action_not_authorized` 等不一致错误。
- 整改：建立单一 `CapabilityDecision`/`EffectLifecycle` 结构，由一个策略层输出 allow/deny/reconcile；执行器只消费结构化决策，不重复解释字符串。
- 验收：每次工具调用只有一个最终授权决定；拒绝原因、策略版本、对象摘要和是否已启动外部调用均写入审计。

## 推荐状态机

```text
候选生成
  ├─ 低风险不可变产物 ── delivery failed ──> 新 generation 直接重试
  ├─ 只读建议/评审 ────── runtime failed ──> 新 generation 重试
  ├─ 高风险外部动作 ───── proposal ────────> needs_human
  └─ 外部调用已开始但无回执 ───────────────> read-only reconciliation

reconciliation
  ├─ confirmed_completed  -> done
  ├─ confirmed_not_started -> failed/no_effect -> new generation
  ├─ evidence_conflict -> needs_human（具体证据差异）
  └─ provider unavailable -> pending_reconciliation（带下次时间和原因）
```

## 分阶段优化方案

### 立即整改

1. 增加 `EffectLifecycle` 持久化字段，停止用 `effect_started_count` 代表外部调用已启动。
2. 给每个任务计算并持久化 `recovery_policy`，禁止普通任务进入高风险 reconciliation。
3. 统一 `needs_human` 生成器，低风险任务不得生成 needs_human。
4. 为每次拒绝记录 `policy_version`、`decision_reason`、`external_call_started` 和 `receipt_present`。

### 近期整改

1. 合并 `AuditAgentRunner.recover`、worker unknown recovery 和 store requeue 的状态转换入口。
2. 为每种 recovery policy 增加状态机测试和进程终止恢复测试。
3. 将高风险动作的人工选项绑定到具体 action index、目标和证据摘要。
4. 增加最近一周质量门：非 done 任务必须有合法的 owner、lease、下次时间或人工决策原因。

### 持续治理

1. 每周统计同一 generation 的重复 attempts，超过阈值自动生成工程告警。
2. 将安全策略版本与部署提交绑定，禁止代码与生产策略漂移。
3. 对所有外部写入保留 intent、authorization、start、receipt、readback 五段证据链。

## 当前生产任务的合理性判断

- 供应商付款审批：高风险，pending reconciliation 合理，不能直接重发。
- 普通 PPT 评审、内部沟通、请假通知、项目初审、模板咨询、会议跟进、普通提醒：长期 pending/processing 不合理，应走低风险新 generation 重试。

## 审查限制

本报告未修改生产数据库，也未把 unknown 或 pending 伪造为 success。等保代码审查脚本的模式扫描在脱敏函数处出现 `IndexError`，因此本报告结论以人工阅读真实调用链和生产只读读回为准；该脚本本身应作为独立低优先级缺陷修复。
