## Minimal source allocator reservation

`app/task20_definitions.py:888-952`, `app/task8_storage.py`, `app/task20_schema_release.py:183-278` and `tests/test_task8_allocator.py` provide an already installed exact precedent. A single internal `sqlite_sequence` row `tasks:published` separates the original eight kinds' reservation water from the shared physical allocator. Copy this mechanism's meaning for Runs, rather than restoring an earlier captured numeric value:

1. Forward captures the **current** native Runs sequence immediately before bulk transfer, separately retaining original presence versus absence as declaration-transport metadata. Capture/preparation time is not the current water. Transfer every old row with the original physical ID and every original scalar/type. Preserve deleted-high water before inserting new-kind physical rows.
2. Initialize `runs:published` from that current source water after bulk old-eight transfer, with the same zero/absence treatment as Tasks. Bulk explicit inserts must not masquerade as runtime reservations. The initializer owns neither begin nor commit.
3. A finite BEFORE INSERT trigger tracks **only original eight-kind** single-VALUES native attempts. For omitted physical ID, reserve `max(global runs sequence, max(actual physical id), 0)+1` below signed-64 maximum; at maximum let native FULL semantics apply without overflowing the reservation. Match the existing Tasks trigger's explicit-ID branch only for migration mechanics; current original runtime callers omit physical ID. Do not replace original INSERT/IGNORE statements with pre-checks or Python success-only bookkeeping.
4. A successfully ignored original-eight UNIQUE/CHECK candidate still consumes the attempted allocation and must advance `runs:published`. An ABORT rolls back the reservation with the failed statement; caller/savepoint rollback rolls it back normally. Ignored insertion and deletion prove why `max(surviving original id)` cannot recover water. Existing source RAISE(ABORT) triggers retain their own behavior even under OR IGNORE.
5. New source kinds advance shared physical `runs` water but never `runs:published`. Each needs an independent current `runs:<source_kind>` native public AUTO counter/presence stream (the exact source kind names, not a combined metadata sequence). Existing-session metadata UPDATE must not allocate or advance its native stream; its real writer selects then inserts or updates, not SQL UPSERT.
6. Inverse reconstructs current old-eight rows, preserving all62 stored source columns and types and original physical IDs, and sets native Runs water from **current `runs:published`**. It reconstructs each new source table from current new-kind facts and each source's current public counter/presence. Remove internal prefix rows after restoration. Do not copy target global Runs water back into old source Runs, and do not restore stale saved counter numbers. A declaration check must exclude mutable allocator state.

Example of the distinction: old source water 10, internal metadata physical11, then old-eight OR IGNORE attempts physical12. No new old-eight row exists, but its current restored source water is12. If only the internal metadata insertion occurred, restored source water stays10. These histories can have indistinguishable surviving old rows; the source reservation is required. Global water and current old source water answer different questions.

This is a proposed reuse, not proof of new Runs behavior. Native FULL, ignored CHECK/UNIQUE, error precedence, cursor `lastrowid`/rowcount, rollback and savepoint behavior require the actual/fresh differential matrix before application. New source tables have no native BEFORE triggers, while the shared Runs container does; Tasks12 already treats native AUTO FULL transaction scope explicitly (`app/task12_storage.py:153-181`). Do not assume one target trigger's native failure scope automatically matches all three sources. The signed-64 exhaustion/positive physical-ID case also needs explicit source-backed characterization rather than silently inventing a new allocator policy.

The observed old-eight runtime contract is bounded: `insert_run` emits a single `VALUES` statement with native INSERT or OR IGNORE and source-kind defaults; current callers omit physical ID. The original helper normalizes supplied `legacy_key` via `str(int(...))`. Existing migration writers explicitly supply physical/public IDs. Arbitrary multi-row insertion, manual sequence editing and OR FAIL are not established runtime guarantees by this inventory. Keep historical `create_run_schema`/declarations exact as genuine predecessor oracles.

## Composition and tradeoff

Consolidating the two already approved Runs-directed families alongside metadata in one target declaration/rebuild is preferable **if** the complete native profiles, callers, constructors and independent counter protocols are proved together. It retires three ordinary tables (54→51 before other groups), keeps Runs as one core and avoids rebuilding231340 wide rows a second and third time. It is not evidence of final11 or production acceptance. Deferring either source is smaller initial caller scope but knowingly repeats a wide Runs rewrite and another exact-shape release transition.

`configs_run_schema._declarations` exact-binds `_declared_run_objects(True,True)`; `_rebuild` copies every stored column, all `runs`/`runs:*` waters and compares every value/type. A later Runs extension must compose with its mapped declaration and inverse order. Recommended ordering is new Runs conversion after the existing mapped-FK conversion and new Runs inverse before restoring native config FKs; root must validate this against its full paired coordinator. Do not globally rewrite `_declared_run_objects` or historical source factories so the old translator silently accepts a different source. Current-shape predicates and constructors need a separately exact new target binding. Existing `_waters` prefix scan naturally includes future source streams, but exact current object matching does not yet recognize them.

Root acceptance remains: exact62-column/type/physical-ID preservation, actual/fresh source declarations and allocator presence/current waters, current write/delete/ignore and metadata update behavior, generated-field/source affinity checks if chosen, original/FULL/caller/savepoint differential, coupled constructors in supported orders, current-fact inverse, genuine44ee predecessor public writes and cold reforward, unchanged unrelated/FK baseline, then separate native/UI/business/performance/final11/publication evidence. No implementation or acceptance claim is made here.
