# Email body and training-input lifecycle: source plan and current implementation boundary

The original source analysis below records the initial dependencies after canonical Email R3. Exact full-body adapter, observed-current-folder unique Message-ID resolution and current task context integration are implemented and tested with real SQLite/fake IMAP (105 focused tests, 13.59 seconds); unobserved movement, historical source availability, terminal-body migration, thread history, legacy model_text consumers and physical retirement remain unfinished. Current selected training and preview now use validated latest external inputs or accurate provider inputs; a full-copy refresh proved 3,766 existing inputs unchanged, and the real paired initializer now prepares it after commit/cold open; the full copy inverse/reforward preserves new dataset metadata and exact inputs. The candidate Console JSON list/detail/unsubscribe/full-text search routes now use bounded account source batches; its search product choice and real provider performance are still pending, and this is not a production deployment. The initial adapter checks used only fake providers; subsequent bounded read-only provider probes are recorded separately in the main acceptance evidence, with zero real sends. Current evidence is in the single final acceptance checklist; historical source line references below are navigation only. The approved target is a completed, accurately retrievable mail whose readable body is no longer a long-term DB cache; `model_text` is a separate sanitized classification/training input kept only for actual current runtime or training dependencies. The target retains business decisions, action plans, retry state, receipts and independent provider inventory. See `docs/superpowers/specs/2026-10-11-database-redesign-design.md` §§2–4 and stage 4. The 30-day successful-poll detail proposal is unconfirmed and outside this unit.

## Exact fields and sources

| `emails.message_normalized_text` (projected as `email_messages.normalized_text`) | Readable stored form. `EmailStore._upsert_message` writes it from scan/label/model paths; `list_classifications`, `list_unsubscribe_classifications`, `get_classification`, `_classification_search`, `list_email_context_thread`, and `list_selected_training_records` read it (`app/email_store.py:8560`, `13203`, `13385`, `13404`, `13512`, `13638`, `14325`). Display additionally parses MIME-like text and filters visible body (`app/email_store.py:241`, `13203`, `13638`). A source read must reproduce the appropriate public *rendered* result and cannot claim stored-byte equality from current provider body alone. |

Deleting the field merely because a newer normalized input exists would break those distinct contracts. |
| No DB corpus: external `*-training-data/<digest>.json` | The folder/selected snapshot observation has `account_id`, `stable_message_identity`, `normalized_model_input`, its hash, schema version, folder/label/split and ordered digest (`app/email_training_snapshot.py:92`, `436`, `524`). `EmailStore.persist_training_snapshot` publishes external file and only metadata/manifest in Configs; `_get_training_snapshot` validates latest/pin and exact DB identity against file (`app/email_store.py:14432`, `15506`; `app/email_training_data.py:22`, `88`). `prune_training_snapshot_data` keeps latest frozen **per actual snapshot version** while training is idle (`app/email_store.py:14567`; `app/email_training_data.py:140`). An observation may be keyed by exact account+stable identity only after validating the **particular current file, version, digest, input schema and label/inclusion state**; a latest file is not a fallback for another run or an arbitrary historical row. It holds canonical normalized input, not necessarily the old `class_model_text` serialization or readable `message_normalized_text`. |
| Separate experiment snapshot | `build_snapshot` consumes `message_id` but serializes `sample_id_digest`, label, model text, date and group digest; it discards direct message/account identity (`app/email_experiment_snapshot.py:19`, `100`). This file cannot be used as an exact keyed mail source. No extra archive, model-input backup or corpus copy is proposed. |

IMAP read-only `fetch_uid_batch` selects by folder/cursor and `_fetch_one_message` fetches bounded text sections (`app/email_imap_readonly.py:447`, `516`); it originally had no public exact-body-by-locator method; the final candidate now adds `fetch_message` for exact account/generation/UID/stable identity, full selected text and attachment skipping. This does not yet coordinate moved locators or establish historical body parity. Current `_reread_historical_candidate_message` checks generation and stable identity but obtains a bounded batch (`app/email_worker.py:3072`); `EmailContextSource._read_current_provider_message` similarly reads a batch and currently falls back to durable body on unavailable/moved source (`app/email_context_source.py:145`). `ImapActionProvider._read_exact` checks UID, generation and optional Message-ID, but reads only flags/header for actions (`app/email_provider_actions.py:849`); `find_states` can search Message-ID and may return multiple matches (`599`). These are pieces for an exact read, not proof that an arbitrary completed message is accurately retrievable. Provider-state stock stays independent; the approved design explicitly forbids deleting unclassified stock to shrink Email (`design.md:28`, `130`, `166`). |

## Remaining runtime dependencies and decisions

1. **Active one-copy input.** Scan/label/model acceptance currently builds readable and sanitized forms from an in-memory provider message (`app/email_classifier_scan.py:867`, `app/email_worker.py:296`, `app/email_training_labeler.py:373`). Preserve the one active durable input needed for queued classification, Agent review, action/reply/unsubscribe retry, and crash recovery. `EmailContextSource.load_task_input` validates durable classification/plan identity, constructs trigger and related thread text, and optionally refreshes the trigger from provider (`app/email_context_source.py:29–143`). `EmailTaskProducer` and worker recovery also use thread rows (`app/email_task_producer.py:124–241`; `app/email_worker.py:2259`, `2400`). `processed` classification alone is **not** a retirement signal: action plans, feedback, claimed tasks, uncertain external effects and manual correction can still depend on body. Keep metadata-only actions and all completed receipts even when body retires.
2. **Readable body readers.** List/detail/unsubscribe pages and body query currently use SQL body projection; `_classification_search` applies `email_visible_body` inside SQLite to every matching row (`app/email_store.py:13385`). The context reader and worker need body for trigger/related messages. Build an explicit body-resolution result (`available`, `unavailable`, `identity_mismatch`, `source_error` plus the appropriate rendered text when available) at the Email service boundary. Resolve outside any `EmailStore._connect` write transaction and never perform provider I/O under a writer lock. Metadata pagination/count can stay SQL; body search needs a proven semantics/performance path before retiring rows whose body it must search. IMAP `SEARCH TEXT` alone is not proven equivalent to current display filtering; do not silently turn a body hit into a metadata-only search result or render an empty string as though source were empty. The UI/API must display source unavailability honestly.
3. **Exact provider read.** Add a read-only public adapter operation targeted at retained account+folder+UIDVALIDITY+UID, verifying returned UID, stable identity and (when present) RFC Message-ID. For moved mail, use current provider-state locator/action readback and only an unambiguous identity-matched candidate; account, folder inventory and generation changes must be explicit unavailable/mismatch outcomes, with no nearest/latest message fallback. Recheck identity after retrieval and before returning text. The existing `fetch_uid_batch` cursor/limit and action header-only primitive are insufficient as a generic completed-body contract; tests must prove missing UID, reused UID, changed UIDVALIDITY, duplicate Message-ID, moved folder and message-only canonical row. Exact byte parity of old stored `normalized_text` is not presumed because writers stored differing forms.
4. **Model input and current training.** `provider_model_input_fields` takes provider `textBody`, approved headers, recipients, unsubscribe features and attachments; `canonical_model_input` is versioned `email-folder-model-input-v4` with earlier frozen versions readable (`app/email_training_snapshot.py:29–41`, `893–923`). `list_selected_training_records` currently reconstructs normalized input from DB readable body and stored metadata (`app/email_store.py:14325–14430`); this drops provider-only fields (notably Cc/unsubscribe features) and is not proof of parity with a frozen provider observation. Refactor this reader to use an exact current provider message or an explicitly validated current external snapshot observation whose account+stable identity, version, digest, label and source match the requested selection. A frozen observation can preserve *that snapshot's* input for a pinned training run, but it cannot retroactively reproduce old `model_text` or a changed owner label. Retain `class_model_text` while similar examples, classic training/inclusion CAS or other current callers still require that exact text; if changing those consumers to versioned normalized input is independently approved and equivalence proven, update them and inclusion invalidation coherently rather than nulling the field under existing reads. Preserve manual selection, preview, label correction and training functionality (`app/email_classifier_learning.py:78–180`, `327–412`; `app/web_api/email.py:1849–1965`).
5. **Training snapshot dependencies.** Training children read pinned frozen data, then compare current sample digests/inclusion against DB before promotion (`app/email_store.py:14550`, `15506`, `15705`; `app/email_classifier_training.py:82`, `170`). Keep the latest external baseline for each actual snapshot type and any active run pin until its reader finishes; leave metadata, manifest, model binding and business outcome readable after older data retires. The separate model policy is current + previous runnable + latest readable candidate, with the 2026-10-18 source inventory reporting three external weights totaling 118,342,536 B and two current external training files totaling 26,507,412 B (one per type); 93 staged and 110 run files are metadata/evidence, not DB corpus (`docs/database-redesign-latest-model-retention-audit-20261017.md:7–55`, `60–166`). These are earlier readbacks, not fresh measurements or authority to delete files. Do not remove the previous runnable model to satisfy a shortened “latest” phrase.

## Finite implementation sequence

| Unit | Change and acceptance boundary |
| --- | --- |
| A. Exact source reader | Read-only provider body operation plus Email service resolver keyed by account+stable identity/current locator. It returns text with provenance/identity result, never substitutes another row; no DB write or source fetch under transaction. Prove message-only and moved/ambiguous/missing cases with fake IMAP and store fixtures. Record exact source/hash availability in a rehearsal report without dumping bodies. |
| B. Caller integration | Convert list/detail/unsubscribe/context/worker, manual rescan and training selection/preview one caller family at a time. Preserve list totals/filter semantics and original rendering; make unavailable explicit. Keep existing on-disk body while differential tests compare old/new responses and provider unavailable behavior. Body search is a separate mandatory parity gate, not an incidental metadata-only downgrade. Model-input selection binds exact snapshot identity, schema/digest and current label; classic/similar-example consumers remain on `class_model_text` until an independent parity conversion passes. |
| C. Transaction/lifecycle integration | Define eligibility from existing task/claim/action/feedback/retry/receipt states and exact source availability, not age or `class_status='processed'` alone. Freeze current/claimed input version; retire only after all active dependencies finish and reader parity/source proof succeeds. Perform eligibility recheck and transient-body null in one short DB transaction; provider I/O and hash proof happen before it, followed by a version/locator/state recheck in transaction. Recovery must not resurrect actions or erase provider-first receipts. Never roll back to a stale DB after a send window; use compatible inverse or forward repair preserving new receipts (approved design §5). |
| D. Physical schema and migration | Only after A–C are proven, allow nullable/transient `message_normalized_text` and, where all exact consumers have been converted, `class_model_text`; update canonical definitions, projection/codec, old `NOT NULL`/body triggers, source copy and inverse profile together. Keep stable IDs, message-only rows, live locator updates, provider_state, classification/plan/inclusion identity and action FK/CAS intact. Migration copies existing bodies once; rehearsed retirement handles only rows satisfying the full dependency/source predicate. Source backups cannot supply bodies for **new post-forward rows** during rollback: a compatibility inverse must preserve those transient bodies and all new actions/receipts, or defer physical retirement until rollback no longer needs old-body `NOT NULL`. No old-code restart on new schema. Report changed body bytes/page/WAL only after actual rehearsal/production measurement; table count is not the objective. |

Use existing focused coverage first: `tests/test_email_store.py` (body display/search, rescan, feedback, training inclusion/CAS and current canonical fixtures), `tests/test_email_context_source.py`, `tests/test_email_training_storage.py`, `tests/test_email_training_snapshot.py`, `tests/test_email_experiment_snapshot.py`, `tests/test_email_classifier_learning.py`, `tests/test_email_imap_readonly.py`, `tests/test_email_training_labeler.py`, and the matching Email web API/action/recovery tests. Add narrow regressions for exact source identity, body-form differential, unavailable UI/search, active action/feedback/recovery hold, latest/pin identity, label change invalidation, and forward/inverse post-send receipt preservation. Do not run the whole live-tree test suite. Update `docs/architecture.md` and `docs/runtime-mechanism.md` in the implementation commit when behavior actually changes, per repository instruction.

## Explicit source gaps before selection

* No source evidence here proves the current provider can reproduce every historical stored readable body: bounded text fetch, folder move and Message-ID ambiguity need row-level reconciliation. Rows failing exact recovery must remain visible as unavailable; they are excluded from automatic retirement rehearsal, not silently marked retrievable.
* No source evidence proves all `class_model_text` rows can be regenerated byte-for-byte under the current normalizer, or that the latest training file covers every current classic/similar-example dependency. `email-experiment-snapshot-v1` lacks direct identity. Until the relevant consumer conversion/equivalence is proved, those inputs stay.
* Body-search parity, current per-row active dependency counts, byte savings and rollback of post-forward rows require a later isolated database/provider rehearsal. This source plan supplies gates, not those results. No new business field, age policy, provider-stock pruning, algorithm downgrade or permission step is implied.
