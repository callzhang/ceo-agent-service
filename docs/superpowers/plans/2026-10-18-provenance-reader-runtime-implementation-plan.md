# Provenance reader and Business Signal runtime closure: implementation plan

This is a source-derived plan for the **next finite reader/model/transaction slice** of the approved [database redesign](../specs/2026-10-11-database-redesign-design.md). It selects no schema, migration, runtime caller, source-body retirement, or release. Source navigation is pinned to worktree HEAD `8eae51e05af4a47032622680aaec2b689a6e13f8`; line positions and concurrent code can move. The current selected intermediate has 12 ordinary tables, including `business_source_documents` and `business_legacy_links`. The independently claimed Legacy inline owner component is separate and must not be edited by this unit. The final goal remains ten core tables plus one migration ledger, with only truly shared exact source versions in body-free `provenance` and unique owner facts inline.

The approved rule is to retain adopted quotations, business results, evidence roles and real multi-source associations while retiring *retrievable original body copies*. It does not authorize moving the old body into `actions.payload_json`, another table, a local archive, a cache, or a native trajectory copy. A source URL, content hash, or version key is a locator/check, not the original text. The planned reader must return either a checked complete body for this exact version or an explicit unavailable result. The selected storage still supplies `evidence_text` via body joins, and `BusinessTaskSignal` requires both `source_document_id: int` and nonblank `evidence_text` (`app/store.py:4037-4045,4213-4231,4358-4380`; `app/task_semantic_models.py:164-179`). Returning `""` to satisfy that model would be false and invalid.

## Source binding to implement, before any body or DDL removal

1. Define a small immutable **source version binding** and a transient **read result** in a new `app/business_source_reader.py` (name subject to the implementation owner's file claim). The binding holds existing Signal facts (`source_type/ref/time`, conversation and author fields, `author_kind`, `dedupe_key` where comparison needs it), the existing `business_source_documents.identity_key`, exact complete-body SHA-256 and UTF-8 byte count derived from the still-present body or an incoming `SourceSignal.evidence_text`, and a *real* exact locator when one is known. For a native version the locator is the existing `native_provenance` mapping; for a provider version it is the exact UUID or node/historyVersion plus existing source-ref identity, never an inferred title or current URL alias. These are source identity/check facts allowed by the design, not new business fields. Do not claim a provider history version merely from an `ai_minutes` `#todos-sha256=` suffix: `app/task_scanners.py:207-258,312-395` makes that suffix an action-set queue digest rather than a full-body or provider-version digest.
2. The read result is a tagged value such as `available(body, binding)` or `unavailable(binding, reason)`, with `body` present only in the available branch. Its body exists in process memory for the one request/decision, not in persistent storage. Reasons distinguish at least missing exact locator, source missing/incomplete, and exact version/body mismatch; none creates a substitute source. Native `LookupError` and invalid-coordinate `ValueError` from `read_native_source_body` remain their actual causes internally. An unavailable result does not erase a Signal, an adopted fact, or a prior quote; it simply cannot satisfy a new historical quote check.
3. Compute `source_document_key` with its *unchanged* eight-element identity tuple (`app/task_source_documents.py:43-65`) when a complete body is read. Compare the resulting identity key **and** body SHA-256/UTF-8 bytes with the binding, then check the exact `source_ref` and quotation through existing `source_contains_quote` (`:21-40`). The key includes actor/conversation metadata as well as body, so equal body bytes alone do not merge Signals or source versions. Conversely `conversation_title`, `context_json` and `dedupe_key` are not in that key and remain independent dedupe comparisons. Keep `SourceSignal` (`app/task_semantic_service.py:51-65`) as a transient incoming object with nonblank evidence: current-source date, suggestion and acceptance checks already use that supplied text. Do not persist another full copy from it.
4. Use a **single request-scoped map by exact identity key** for readback. Multiple Signals sharing a version get one body fetch and distinct Signal IDs, author/context facts and evidence roles. A formerly unique version that becomes shared is represented by the same exact identity key when the second Signal arrives; the eventual schema migration promotes that binding to `provenance` and rewrites both FKs in one migration transaction. A changed body, source ref, author, or source time gets a different key even when a provider node is the same. The map is discarded after the request; it is not a durable cache.

The selected Signal rows do **not** contain native coordinates: the current `context_json` readback has no `native_provenance` key (`docs/database-redesign-live-source-readback-20261017.md`, Signal dependency section). The verified native coordinates live in metadata-only proof receipts, and the 130 historical provider checks are older observations. The physical unit must validate each exact coordinate against the copied source and persist only the selected locator/check metadata on its inline owner or shared `provenance` row; runtime code must not read a research receipt as an operational database. A row with no proved coordinate stays explicitly unresolvable, not assigned a guessed session or provider version.

## Ordered implementation units

**A. Unselected reader/model component, with the old table still intact.** Add the exact binding/read-result types, a separate `BusinessTaskSignalFact` metadata model, and source-kind adapters above. Do not change the selected `BusinessTaskSignal` or Store yet. Synthetic tests supply native/provider coordinates and prove both available and unavailable results without constructing a target database or reading a real provider. The current selected Store can later derive the same binding from its old body under a read connection; the target projection gets it from body-free metadata. A detail response can eventually include `evidence_text: null` only alongside explicit `source_status: unavailable`, or use an equivalent discriminated source object. It must not imply `null` means an empty original.

**B. Caller integration after A passes.** Replace the four current body-joining leaf queries (the dedupe lookup, task/source-ref lookup, list and ID lookup at `app/store.py:4037-4045,4213-4231,4358-4380`) with fact/binding projections; keep the two public wrappers as wrappers. Change `BusinessTaskSignal` and the direct Signal API in `app/web_api/registration.py:563-575` plus Task/Project/Attention envelopes in `app/web_api/tasks.py:799-854,1197,1272` together so serialization exposes source availability honestly. A distinct `resolve_business_task_signal_source(signal_id or binding)` runs only *after* leaving any Store write transaction. While the old table remains selected, this resolver's backing is its one original body under a read connection; the body-free provider/native backing is tested as the target and replaces that backing in the physical unit, not as a per-row failure fallback. `_business_source_document_id` and its call in `create_business_task_signal_in_transaction` (`:4048-4064,4066-4116`) stay selected until that physical unit. Change `TaskSemanticService._require_same_signal`, `_signal_id_or_create`, `_replay_result` (`app/task_semantic_service.py:201-251`) to compare incoming `SourceSignal`'s computed identity/body checks with persisted metadata while also preserving source type/ref/time, conversation ID/title, author ID/name/kind, context JSON and dedupe key. It must still raise the existing mismatch on any changed field and return the same existing Signal ID on exact replay. `todo_completion.py:21-38` only needs that ID and its incoming evidence; no source fetch belongs inside its write transaction. `app/store.py:6990-7040` is the historical old-source migration, not a runtime leaf to replace by global substitution.

**C. Read outside, bind inside the existing transaction.** Before Task Agent starts `task_agent_domain_apply_transaction` in `process_work_item` (`app/task_agent.py:3258-3355`), collect the finite historical Signal IDs reachable from the decision: project/context/attention citations, stored Attention card proof, referenced acceptance and any `same_source_item_same_owner` identity proposal. The same preflight runs before standalone `apply_task_agent_decision`; when its `_db` argument is already a writer connection, its caller supplies the prepared map. The preflight reads fact/binding rows with a read connection, resolves each exact version once outside the writer lock, and checks the complete body/quotes. Inside `apply_task_agent_decision` (`:1699-1725,2539-2546`) reselect each used Signal by ID and compare its immutable identity key/hash/bytes, source ref/type and the exact linked evidence/task/project IDs against the prepared binding before mutations; then check quotes against the already resolved in-memory body. If the selected row/link differs or the body was unavailable, reject the citation through the existing validation outcome. This is identity revalidation for a read/write race, not a new review, authorization or audit gate.

`_resolve_project_citation` and stored Attention checks (`app/task_agent.py:1403-1434,1635-1675,2690-2725`), `_validate_identity_proposal` (`:3058-3225`), `ProjectContextService._require_signal/apply` (`app/project_context_service.py:45-105`), and `TaskSemanticService`'s historical acceptance/reference checks consume that prepared map. `ProjectContextService.apply` can take an additional `resolved_sources` argument keyed by Signal ID: its `_require_signal` remains a metadata/link read, and the quote check uses the supplied body after binding revalidation. It must never call DWS/native readers from its transaction. Current Work Item citations still check the transient `work_item.summary` and need no historical fetch. The subsequent `_project_task_attention` transaction (`app/task_agent.py:2630-2730`) has the same prepared binding available and rechecks it in that separate transaction.

**D. Read-only context, bundle, and backfill callers.** `task_retrieval._source_backed_owner_signal_id` (`app/task_retrieval.py:92-135`) and `render_task_semantic_context` (`:373-395`) resolve only needed historical bodies outside a writer; unavailable originals cannot prove an owner or quote, but retained task owner/evidence facts stay visible with unverified source status. `task_source_documents.source_bundle` (`app/task_source_documents.py:138-229`) groups by exact existing `identity_key`, not by source type/ref or body hash. It preserves the **existing `document_id` prompt grouping role**, using that stable key as its value and the same value for every Signal of that version; no new numeric counter or old `source_document_id` alias is needed. Keep bounded visible ranges and decoded quoted leaves for available originals. For unavailable originals include explicit source status and locator metadata; do not report a fake zero-character source or claim `full_length` when only UTF-8 byte count is known. The current Work Item still uses its supplied summary and exact key to join an identical historical version.

`minutes_owner_backfill.ownerless_candidate_meetings` (`app/minutes_owner_backfill.py:57-77`) is a fifth direct SQL body consumer outside Store: it parses `document.body["meeting"]` only to build a *new* Work Item. Select candidate minutes UUIDs and task IDs from Signal facts, then obtain the exact current meeting record via existing `get_minutes_info` or an exact UUID match from `list_minutes` before building the new canonical item. If no exact current record is readable, keep the existing skipped outcome and do not infer a meeting from an old body. The provider reads already occur outside its short Store reads/writes; preserve that boundary and the digest/backfill idempotence.

**E. Later physical provenance/inline unit, only after A–D tests and source availability work.** Define the one body-free `provenance` declaration for exact versions that genuinely have multiple owners, plus inline identity/locator/hash/bytes on an unshared `actions.signal_fact`. Preserve the existing Signal public ID and `dedupe_key`, author/context facts, task/project evidence rows with their distinct roles, adopted small source excerpts and business results. The present `source_document_id` is an internal FK to a table being retired; its only confirmed runtime grouping use is `source_bundle`, and the direct API currently exposes it through `BusinessTaskSignal`. Convert that API and bundle in A/D rather than committing a permanent numeric alias for each retired source row. Actual sharing is measured by references to one `identity_key` (80 unique and 133 shared among the older 213-row readback), not by equal links, names or hashes. At migration time recompute counts on the actual copied source and handle a unique-to-shared transition atomically.

The migration forward/inverse must preserve every Signal's ID, fields/types, exact identity and all inbound evidence/action FK relationships; prove shared and inline projections return the same bindings. It removes old `business_source_documents` body/NOT NULL/immutable triggers and `source_document_id` only when the body-retirement criterion is met. The old declaration requires `business_source_documents.body NOT NULL`, unique `identity_key` and immutable rows, while Signals require a nonnull document FK (`app/store.py:1011-1063`). A frozen source backup is a bounded **rehearsal oracle** for rows that existed before forward migration, and may supply those original bodies in that rehearsal. It is not a general inverse: it cannot contain Signals, relations, receipts or source versions written after forward migration. No full-body copy belongs in the target merely to make inverse easy.

Before selecting this physical unit, specify and prove the inverse against the **current target state**, including post-forward Signal/evidence/action writes and any new external receipts. For every Signal that did not exist in the frozen source, the inverse must obtain its exact complete body through the recorded source locator, verify body SHA/bytes and `source_document_key`, materialize one valid old source-document row, and link the Signal and every new relation with original ID/uniqueness semantics. For old rows the rehearsal compares against the frozen source and must still preserve all current target updates. If a post-forward source has no exact recoverable body, the old body's `NOT NULL` and Signal FK cannot be satisfied honestly; neither a blank body nor a stale backup is an inverse. The physical release design must therefore prove a reversible post-forward write contract **or** report that old-schema rollback is unsolved and select a safe forward-repair path before activation, especially once outbound effects can create new receipts. The approved design already forbids rolling back to a stale DB after the external-send window opens (`../specs/2026-10-11-database-redesign-design.md`, stage 5). This plan chooses neither a new write restriction nor a rollback mechanism. The selected old table and its source bodies remain until the unproved-row decision below; reader/model/transaction work can finish first. No DDL or inverse in this plan is selected by writing this document.
