## 结论先说

每晚 21:00，服务先把自己当天记下的事导出成一份材料交给 Agent；Agent 再扫当天群消息，
写一份七段报告，存成当天的钉钉文档，然后以 Derek 本人身份单聊发给「磊哥」（Derek 2026-09-24：不用机器人）。

关键设计只有一条：**报告的必需材料全部来自服务自己的记录，任何一个来源读不到都照常出报告，
不停下来问 Derek 要材料。** 这条是从周报的失败里来的，见下一节。

## 为什么不照搬周报的做法

最接近的先例是定时任务 #13「准备 CEO 管理周报」，同样是 Agent 定时任务。2026-09-19 它跑了两次，
都没有产出：

- 周报 Skill 把「上期周报、公司 OKR、四条业务线来源报告、目标文档」列为必需输入，这些服务读不到；
- 审核 Agent 判定信息完整度低于 0.5，按规则只能改成向 Derek 补要材料；
- 它还拒绝把触发时间当成报告日期，又打回了一轮；
- 来回 4 轮之后，结果是一个追问，而定时任务没有会话，这个追问没有人收到（reply_task 384444，
  run 20182–20190）。

所以日报的做法是：必需材料只有服务导出的那一份；日期就是触发当天，不需要确认；群消息和听记是
补充，读不全就写进「覆盖说明」。这三条都写进了 Skill，目的就是让审核 Agent 不再有打回去要材料的依据。
**这一点还没有被真实运行证明**，首跑时要重点看审核轮是否仍然打回。

## 它每天做什么

```text
21:00 定时触发（暂停状态，需手动启用）
  -> 执行 Agent（按 ceo-daily-report Skill）
       1. 运行只读命令，取当天事实                    （必需）
       2. 扫描当天全部可访问群聊消息                  （补充）
       3. 需要时补读会议听记摘要                      （补充）
       4. 写七段报告
       5. 提出两个外部动作：写钉钉文档、单聊发给磊哥
  -> 审核 Agent 核实后执行，读回 -> 反馈/修订（标准生命周期，最多三轮）
```

走的是现有的 Agent 定时任务通道（Scheduler → Dispatcher → Consumer → Audit），没有新队列、新表、
新投递通道。

### 报告窗口

窗口从**上一份成功发出的日报**的截止时刻开始，到本次触发时刻为止（Derek 2026-09-24 选 B）：

- 截止时刻 = 本次定时触发的 `scheduled_for`；报告日期 = 截止时刻的北京日期，也是文档标题里的日期。
- 起点 = 同一定时任务、报告日期**早于**本次、且**真正发出了报告**的最近一次运行的截止时刻。「发出」指执行任务
  `done` 且最后一次处理结果为 `completed`；「无需处理」或「线路不可用被跳过」的运行任务状态也是 `done`，不算。
- 从没有成功过（第一次运行）时，起点是截止时刻前 24 小时。
- 中间断了几天，下一份自动覆盖断掉的这几天。
- 同一天手动重跑：报告日期相同，所以起点仍是前一天那份报告的截止时刻，窗口覆盖原窗口再多到重跑时刻，
  文档按标题覆盖同一篇。
- 21:00 之后结束的会议落进下一份报告。

实现上导出命令改为 `daily-report-facts --scheduled-run <触发记录 id>`，由服务从触发记录和该任务的运行历史
算出窗口，不由 Agent 自己推算；触发记录 id 已在定时任务交给 Agent 的触发信息里。

### 第 1 步：服务导出的事实

命令：`<服务 Python> -m app.cli daily-report-facts --scheduled-run <id>`（第一版为 `--date`），实现在
`app/daily_report_facts.py`。它只读，不改任何记录；在 `app/native_cli_metadata.py` 里登记为服务只读
命令（和 `read-oa-approval-detail` 同一张表），否则 Agent 调它会被当作未知的本地命令。

下表的「当天」均指上面的报告窗口（第一版按北京时间整天）；比较时统一换算成 UTC（库里时间戳是 UTC）。

| 内容 | 来源 | 口径 |
|---|---|---|
| 会议 | `meeting_alignment_jobs` | 当天结束、且会后跟进消息**已发出**的会议：标题、参会人、发到哪、跟进消息全文 |
| 当天变化的业务 Task | Task-first `business_tasks` + `business_task_events` | 最后活动时间落在当天的 Task，附当天的变化事件 |
| 业务需关注项 | Task-first `business_attention_items` | **全部**未解决的项（不只当天新增），标出哪些是当天新出现的；带类别（decision / push / watch / fyi）和建议 CEO 动作 |
| 重要邮件 | `email_actions` + `email_classifications` | 窗口内**已执行**「标为重要」动作的邮件，即邮箱里实际被标重要的：发件人、主题、分类、摘要 |
| 当天处理过的事项 | `reply_attempts` | 当天产生的处理记录；「无需处理」（skipped）只计数、不列明细 |
| 等 Derek 处理的事项 | Attention 现有的两条查询 | 与 Attention 页同一口径：审核结果确实判为「需人工」的事项 + 未决的 OA 审批 |
| 投递对象 | 服务记录 | Derek 的钉钉 userId |
| 覆盖计数 | — | 每类读到多少条 |

长文本字段截到 600 字。2026-09-24 对线上库试跑：13 场会、35 条已处理（另 26 条无需处理）、
6 条等 Derek 处理，输出约 52 KB。

「重要邮件」沿用邮箱现有的判定，不另立标准。这个判定目前有噪音：2026-09-24 被标重要的 7 封里 5 封是
OpenAI 登录验证码（大多由邮件分类 Agent 把「通知」类标成了重要）。所以 Skill 要求 Agent 只写有管理含义的
邮件（请求、审批、客户、合作方、法务或资金），其余计数。噪音本身属于邮件分类，另行处理。

### 第 2–3 步：群消息与听记

Agent 用 `dingtalk-chat` 按会话分页读当天全部可访问群消息，只摘有管理含义的内容（承诺、计划变更、
分歧、升级、客户或融资信号、卡住的工作），其余计数。会议的跟进消息不够用时，用 `dingtalk-minutes`
读听记摘要。

### 第 4 步：报告结构

标题 `CEO 每日总结 YYYY-MM-DD`，七段：

1. **今日要点**：3–5 条，只读这一段也够用
2. **重要事项进展**
3. **风险**：事实 / 影响 / 建议动作
4. **需要你介入**：只有 Derek 能做的决定或动作，按紧急度排；必须包含全部「等 Derek 处理」的事项和
   类别为 decision 的需关注项
5. **需关注**：还没到要你出手，但在变坏的；从 push / watch 类需关注项开始
6. **管理建议**：基于上面事实的判断，明确标成判断
7. **覆盖说明**：每个来源读了多少，哪些失败或不完整

每条都要注明出处（会议名、群名、Task / 需关注项 id、处理记录 id）；事实、他人说法、判断分开写；
空段写「无」，不凑内容。

### 第 5 步：投递

1. 知识库「🎯  目标与执行」下的文件夹「CEO 每日总结」（没有就建）。先按标题找当天文档：有就覆盖，
   没有就新建；写完读回核对。
2. 以 Derek 本人身份单聊发给「磊哥」：今日要点、需介入几条、当天文档标题和「CEO 每日总结」文件夹链接。走服务的已审核消息通道
   （`send_approved_dingtalk_message`），不从命令行直接发；正文在执行轮由服务定稿，那时文档还没建，所以放文件夹链接。

除这两个写入外全程只读：不在群里回复、不改 Tasks、不给其他人发消息。
