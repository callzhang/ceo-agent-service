# 同一次 Task Agent 处理中的显式项目关注判断

日期：2026-10-02。Derek 已选择方案 A，并以“OK”确认本书面设计；进入实施，尚未验证或发布。

## 目标与已确认事实

保留一个共享逻辑 session 的 Task Agent，以及唯一的 `scan evidence → Task Agent → update Tasks` 路径。在同一次处理中，明确记录本轮相关项目是否需关注及其理由，区分“评估后不展示”“证据不足”“漏评”与“判断需要、但应用失败”。不增加 Agent、后台维护、补偿检查或自动补卡。

现有验收记录证明：代码 `c87752c0` 的真实 W39 新副本更新六个已有 Task，无重复 Task；中汽创智与岚图已按当前正式登记名称关联。原文存在收入确认延迟、付款节奏和结算争议，但六条决定的关注提案全部为空，回执为 `no_proposal`，0 张卡片。最终摘要没有说明两项具体风险为什么不关注。当前字段无法证明 Agent 已评估它们，也无法准确确定内部遗漏原因。

这次改动首先补齐可观测的判断契约，不保证模型因此必然判断正确。真实业务结果仍须单独验收。

## 已比较的方案

- A（已选）：同一个 Agent 显式返回项目判断与理由，并与现有提案及应用回执关联。增加少量结构化输出，能够定位漏评、错误判断和应用失败。
- B（未选）：只调整提示词，保留可省略判断的契约。代码改动少，但关注为空时仍可能无法定位原因。

## 本轮范围与输出

Task Agent 返回值增加项目关注评估集合，与 `task_decisions` 同属一次输出。每条评估保存：

- 项目指向：已有正式项目的真实 anchor，或本轮明确项目登记提案的决定位置；尚未确认的项目保留原文名称与引用作为线索，不凭评估注册正式 Project。
- 判断：`需关注`、`不需关注`、`证据不足`三者之一。
- 理由：具体经营影响或缺少什么证据，不允许仅写“没有风险”“一般情况”等空泛结论。
- 依据：当前原文或已保存原始 Signal 的可核对引用，沿用现有来源、时间、链接与历史比较规则；事实与推断分开。
- 关联：本轮支持该判断的 Task 决定位置、真实已有 Task ID，以及相应关注提案或已有卡片的真实身份。新 Task/Project 不猜未来数字 ID，应用后由服务记录实际 ID。

“本轮相关项目”包括当前决定明确登记、明确关联或以已有确认链接处理的项目，以及当前来源中明确涉及可跟踪业务事项、需要解释关注判断的项目。只评估本轮事项，不遍历全公司项目或所有历史；无关小任务不因存在于上下文就进入关注范围。没有确认项目或真实关联 Task 的风险只能记录证据不足，不为卡片制造 Task 或 Project。

每个相关项目必须有明确判断。同一正式项目多个 Task 共用一个项目判断，不因 Task 数量生成多条业务判断。确定性核对已输出的登记/关联项目是否有对应评估；对语义上漏掉整个项目的情况仍靠固定案例与真实原文验收，不声称结构校验证明完整语义覆盖。没有相关项目时评估集合为空，并在本轮摘要说明原因。

## 判断与应用保持分离

- 需关注：有合格的新风险或变化时，仍通过原有 TaskDecision 的关注提案路径创建或更新卡片；保留现有项目登记、Task 关联、来源验证和同项目折叠机制。
- 已有卡片已完整反映相同事实：判断仍可为需关注，明确引用实际卡片及其已有依据；不为重复事实制造字段变化、重复提案或事件。
- 不需关注：保存具体理由及依据，不产生新卡片，也不自动关闭已有卡片。
- 证据不足：保存缺少的项目身份、真实关联 Task 或经营影响证据，不编造负责人、承诺、日期或行动来补足。

结构不完整或互相矛盾的输出沿用现有解析与一次同会话纠正，不另加 Agent、重试循环或业务审核层。校验关注判断与提案之间的结构一致性；理由是否空泛由原文对照与语义评估验证，代码只验证必填、非空及引用等结构，不用静态词表、阈值或代码规则替代 Agent 的经营判断。

评估日志可以保留判断，但不能绕过 Task 的实际应用约束。原有无字段变化 guard、来源核验及 Task 生命周期不改。若判断需关注而对应提案因未应用 Task、项目关联或来源问题无法落卡，记录“需关注但未应用”及既有应用原因，不把它归为不需关注或静默成功。

## 存储、可观测与文档

原始评估随当前 run 的 `decision_json` 保存；应用读回记录实际 Project、Task、Attention 身份和结果。沿用独立投影回执，不把业务判断成功等同于卡片应用成功。只读检查工具能列出本轮每个相关项目的判断、理由、证据、实际应用结果与失败原因。

既有 `no_proposal` 表示没有提交关注提案，不再作为“已完成项目判断”的证明。显示和验收同时读取评估；缺少评估属于判断输出缺失，不能伪装为明确不关注。历史 runs 原样保留，不回填模型理由，不把旧 JSON 当新契约重新应用。

第一步不扩展业务列表或另建审核页面；需要关注的卡片详情沿用已有事实/推断展示，运行检查入口展示本轮评估。运行 prompt、字段描述、CI Skill、架构与运行文档同步更新；全局 Skill 仍按已批准发布流程在代码部署后发布一致内容，不提前修改生产使用的规则。

## 验收

1. 先写失败回归：相关项目遗漏评估、空白理由、判断与提案结构冲突，以及本轮登记和已有关联项目的覆盖。
2. 覆盖周报、会议、聊天；周报不是唯一风险来源或关注前提。候选 Task 可以支持关注，评估不提升其 stage 或制造接受证据。
3. 同一项目两个独立 Task 返回一个项目判断，卡片仍合并正确成员；未应用提案与明确不关注可区分。
4. 无确认项目、无真实 Task、仅风险标签和普通进展不误建卡；证据不足与不需关注有真实理由。
5. 已有同事实卡片保持身份，无新增 Task/Project/Card 或无变化事件；不需关注不关闭已有卡片，历史运行不被改写。
6. 保留原九项固定样例及新增项目名称竞争样例；同样例、模型、路由、timeout、并发比较，预期不进入 Agent 输入。
7. 精确 W39 新副本两次回放：目标项目身份正确；中汽创智、岚图关注判断与原文经营影响对齐；相关 Task、卡片和引用正确，无重复。模型判断错误则根据已保存理由继续诊断，不能通过强制补卡或放宽预期宣布通过。
8. 实现、局部测试、原生评估、PR/推送、部署、全局 Skill、生产精确回放和页面验收继续分别记录。仍沿原多来源 Attention 计划完成全部发布门槛。

## 不在本次范围

新 Agent、任务维护或完成检查、投影补偿循环、自动外发、工具权限层、项目别名批量合并、全历史扫描、业务关键词分类和模型切换。此 spec 不授权绕过已有 Task/Project 事实约束，也不表示生产问题已解决。

## 自检与下一步

本设计只补同次输出的项目判断及其可观测性；业务判断与实际应用分开，正负结论都不会隐式改变 Task 或关闭卡片。没有占位需求，不与既有共享 session、唯一更新路径、来源优先级和 no-field-change 规则冲突。
