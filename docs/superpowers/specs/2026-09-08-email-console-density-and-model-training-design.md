# Email Console 高密度列表、类型描述与模型训练设计

日期：2026-09-08
状态：已完成视觉确认，待书面 Spec 审阅

## 1. 目的与权威边界

本设计更新 CEO Email Service 的 Console 交互，解决四个已确认问题：

1. `已处理` 与 `待反馈` 单元过高，不能像 Gmail 一样快速扫描；
2. `邮件配置` 没有呈现分类所需的完整语义描述；
3. 原 `学习` 页面没有清楚区分 Agent 主分类、模型影子模式和模型主分类；
4. 模型版本以巨型卡片平铺，无法直观看出能力变化和晋升条件。

本设计补充 `2026-09-06-email-folder-source-and-staged-classifier-design.md`，不改变其
文件夹事实源、分类器运行阶段、重要标签、垃圾邮件和退订生命周期。若旧 UI 文档与本设计
冲突，以本设计为准。

本设计不改变公共任务生命周期、Audit 规则、自动退订或回复授权；不自动晋升模型，也不
让影子模型参与新邮件实时分类。

## 2. 已确认的总体方案

Email 页面保留四个 Tab，但将 `学习` 正式更名为 `模型训练`：

```text
已处理 | 待反馈 | 邮件配置 | 模型训练
```

视觉方案统一采用高密度运营界面：

- `已处理`、`待反馈`：全宽单行列表，点击一行打开右侧详情抽屉；
- `邮件配置`：类别导航加单项编辑，描述使用“核心定义、包括场景、排除场景”；
- `模型训练`：运行模式总览、能力趋势、晋升检查和紧凑版本表；
- 详情、证据和低频字段进入右侧抽屉，不在主列表或主页面铺开巨型卡片。

页面继续使用现有 React、路由、API client 和样式体系，不引入新组件库。

## 3. 已处理与待反馈

### 3.1 共用列表结构

两个 Tab 使用同一个高密度邮件列表外壳。桌面端每封邮件一行，目标稳定行高为
`40–48px`，列顺序为：

```text
重要标记 | 发件人 | 主题与单行摘要 | 类别/模型建议 | 处理状态 | 收件时间
```

- 主题和摘要必须单行省略，不能因正文、附件或处理证据撑高列表；
- `已处理` 显示最终类别、分类来源和当前动作结果；
- `待反馈` 显示模型或 Agent 建议、置信度，不能把建议显示成最终分类；
- important 使用 provider 对应的 Star / Flag 视觉符号，与业务类别分开；
- 分页、页大小、选中邮件和当前 Tab 写入 URL，刷新或返回后保留位置；
- 默认每页 50 封，允许选择 20、50 或 100；后端返回总数和当前页边界；
- 加载下一页时保留已有列表，避免整个页面闪烁或高度跳动。

### 3.2 详情抽屉

点击邮件行后从右侧打开抽屉，列表不跳转到独立页面。抽屉按需读取详情，包含：

- 主题、发件人、收件人、抄送和收件时间；
- 已保存的完整正文；正文不存在时保留当前明确提示，不伪造摘要；
- 附件 metadata，不读取或分析附件内容；
- 分类来源、模型完整版本名、描述版本、配置版本、置信度和候选分布；
- 文件夹移动、Star / Flag、Trash、退订等动作结果和 readback；
- `已处理` 只读；`待反馈` 在抽屉底部完成确认或改类。

关闭抽屉后必须保留当前分页、筛选、滚动位置和已选行。切换到另一行时取消上一封尚未
完成的详情请求，不能让迟到响应覆盖当前邮件。

### 3.3 待反馈连续处理

用户确认类别后：

1. 禁用重复提交；
2. 保存反馈和对应文件夹动作；
3. 当前邮件从待反馈列表移除；
4. 自动选择下一封；当前页没有下一封时选择上一封；
5. 当前页清空时回到合法的上一页；
6. 保存或动作失败时保留当前邮件、选择和错误信息，允许重试。

仅确认分类不创建 Email task。只有既有产品规则明确要求执行 Agent 任务时才创建 task。

### 3.4 窄屏行为

当内容宽度小于 `760px`：

- 合并发件人与主题，隐藏独立“发件人”和低优先级“处理状态”列；
- 保留重要标记、合并后的邮件文本、类别和时间；
- 详情抽屉覆盖右侧约 70% 宽度，不压缩列表列宽；
- 不允许文字变为逐字竖排，长内容仍使用省略号；
- 所有主操作保持键盘可达，抽屉关闭后焦点返回原邮件行。

## 4. 邮件配置

### 4.1 类别导航

左侧显示当前启用的可配置业务类别，右侧只编辑一个类别。初始可配置业务类别为：

```text
工作、人事、法务、融资、个人、通知、外部账单、购物
```

`junk` 仍是模型内部输出，但不是可配置业务文件夹，固定映射到每个邮箱账号的系统
Trash。`important` 是独立标签，映射到 provider Star / Flag，不是业务类别。页面不得
重新显示已删除的 `subscription` 或 `other`。

用户新增正式类别时，名称、三段描述和邮箱文件夹目标必须在一次配置流程中完成；创建或
精确绑定 provider folder 并 readback 成功后才启用该类别。同步方向只允许
CEO Email Service → 邮箱服务器，邮箱中新建的任意文件夹不会反向创建类别。

### 4.2 三段式描述

每个类别必须显示并编辑三个独立字段：

1. `核心定义`：一句话说明该类别的本质边界；
2. `包括场景`：每行一个代表性正向场景；
3. `排除场景`：每行一个易混淆反例，并尽可能指出应归入的相邻类别。

三个字段分别对应后端 `core_description`、`include` 和 `exclude`。旧的单一
`description` 输入不得继续作为可编辑事实源。Agent 分类和 Embedding 描述相似度读取
同一份版本化描述。

保存描述时：

- 创建新的 `description_version`，不覆盖历史版本；
- 显示保存成功后的新版本和更新时间；
- 下一次训练快照记录所使用的描述版本；
- 已训练模型继续绑定原描述版本，不能被配置编辑静默改变；
- 保存失败时保留三个字段的用户输入并显示可操作错误。

Agent 可以根据持续反馈提出描述优化建议，但建议必须在配置中可见并经用户保存，不能直接
修改当前描述或已激活模型。

### 4.3 文件夹与固定动作

编辑区同时显示：

- 当前类别在每个邮箱账号中的 folder binding 和验证状态；
- 高置信度固定动作及参数；
- 类别是否启用；
- 配置版本和描述版本。

系统固定规则单独只读展示：`junk → Trash`、`important → Star / Flag`。不得把这两项
伪装成普通类别文件夹或允许用户配置不一致的映射。

## 5. 模型训练

### 5.1 页面结构

原 `学习` Tab 和文案全部改为 `模型训练`。页面采用“运营总览”方案，顺序为：

1. 当前运行模式和主模型 Toggle；
2. 晋升门槛与逐项检查结果；
3. 能力趋势图；
4. 紧凑版本表；
5. 版本详情抽屉。

顶部不能只显示模型 ID。必须首先用用户可理解的状态说明当前由谁处理新邮件。

### 5.2 三种运行状态

#### Agent 主分类

- 新邮件由 Classifier Agent 分类；
- 模型只做阶段性训练和离线验证，不对新邮件实时推理；
- 主模型 Toggle 禁用；
- 页面说明未达标项目，不显示可切换错觉。

#### 已达标，等待用户切换

- 全部可配置门槛和系统完整性检查通过；
- `模型训练` Tab 和当前模式标题显示红点；
- 主模型 Toggle 启用但保持关闭；
- 不自动晋升，不自动执行历史或新邮件主路径切换。

#### 模型主分类

- 用户打开 Toggle 并确认后，选定候选模型成为主模型；
- 模型接受预测时执行既定分类动作；
- 模型拒判、超时、不可用或完整性失败时才调用 Classifier Agent fallback；
- Model 与 Agent 不并行投票；
- 用户关闭 Toggle 并确认后恢复 Agent 主分类，模型回到影子模式。

每次切换必须记录操作者、切换时间、原运行模式、原模型、目标模式和目标模型，并在成功
readback 后更新页面。请求失败时 Toggle 恢复到服务器事实状态，不能只在前端显示成功。

### 5.3 可配置晋升门槛

默认门槛为：

```text
Macro F1                         >= 0.95
每个当前启用类别的 Precision   >= 0.95
每个当前启用类别的独立验证样本 >= 20
常驻模型端到端 P95 延迟         <= 500ms
```

上述四项可以在模型训练页配置；修改后生成新的 threshold configuration version，旧候选
不会因门槛降低而自动变为主模型。页面必须展示实际值、目标值、通过状态和失败原因。

Toggle 只有在四项门槛全部通过，且 `2026-09-06-email-folder-source-and-staged-classifier-design.md`
定义的系统完整性条件也通过时才启用，包括：当前类别和描述版本一致、模型 artifact 校验
通过、Registry 无异常、评测不存在数据泄漏、important 输出头满足既有质量门槛。完整性条件
不可通过 UI 阈值配置关闭。

红点只代表“有一个可以由用户切换的候选模型”，不是错误告警。用户查看页面后红点不能自动
消失；只有切换成功、候选失效或新评测证明不再达标时才消失。

### 5.4 能力趋势图

趋势图默认绘制最近 10 个有效模型版本的 Macro F1，横轴为模型版本，纵轴为指标值，并
显示当前配置门槛线。用户可以切换查看：

- Accuracy；
- Macro F1；
- 每个类别的 Precision、Recall 或 F1；
- P50、P95 和 P99 预测延迟。

图表只连接使用可比较评测协议、测试集版本和类别集合的点。不兼容版本显示为断点并说明原因，
不能制造连续提升的假象。Hover 或键盘聚焦显示版本、训练时间、样本数、指标和评测数据版本。
没有足够版本时显示明确空状态，不补造曲线。

### 5.5 版本表与详情

主页面版本表每个版本一行，至少显示：

```text
完整模型名与版本 | 生命周期状态 | 训练时间 | 样本数 | Macro F1 | P95 | 完整性 | 详情
```

模型名必须带版本并可追溯，不能只显示无版本的 `model`。状态显示候选、主模型、前一版本、
已拒绝、失败或已归档。

点击详情打开右侧抽屉，包含：

- Accuracy、Macro F1 和每类 Precision / Recall / F1 / support；
- important 输出头指标；
- 分类阈值下的接受覆盖率和接受部分准确率；
- 训练开始与完成时间、总样本和新增样本；
- 各类别、邮箱账号和事项组覆盖；
- 模型家族、Embedding 版本、描述版本、输入 schema 和训练数据版本；
- 参数、seed、评测方法、模型 artifact SHA-256；
- P50 / P95 / P99、首次调用和加载耗时；
- 生命周期记录和失败、拒绝、晋升或替换原因。

详情抽屉是只读证据页。大字段允许折叠或复制，但不能在主列表直接展开。

## 6. API 与状态边界

实现计划应优先扩展现有 Email Console API，不让 React 组件推导业务事实。后端需要提供：

- 分页邮件列表的 `items`、`total`、`page`、`page_size`；
- 邮件详情的完整正文、附件 metadata、分类和动作证据；
- 当前运行模式：`agent_primary` 或 `model_primary`；
- 当前主模型、达标候选、红点状态和 Toggle 是否可用；
- 每项门槛的目标、实际值、通过状态和原因；
- 可比较的模型历史序列和版本详情；
- 描述三字段、描述版本、folder binding 和系统固定映射；
- 带幂等键的运行模式切换命令及切换后 readback。

前端不能自行根据几个聚合指标启用 Toggle；它只展示后端给出的 `promotion_eligible` 和
逐项证据。Registry、artifact 或数据版本异常时，后端返回不可晋升状态和明确问题；页面仍应
允许读取历史版本，不能因一个坏 manifest 让整个 Tab 崩溃。

## 7. 加载、错误与空状态

- 列表、详情、配置和模型证据分别加载，局部失败不清空其他已加载区域；
- Registry 异常显示具体模型和失败原因，并保持健康版本可见；
- 无已处理邮件、无待反馈、无训练版本、无可比较趋势分别使用专用空状态；
- 保存配置、确认分类、切换模式防止重复提交；
- 切换模式、文件夹创建和邮件移动必须以服务器 readback 为成功标准；
- API 返回未知类别或旧版本字段时显示原始可追溯值，但不能把已删除类别重新放入可选项；
- 错误信息必须说明用户能否重试、是否需要修复配置，不能只显示内部错误代码。

## 8. 可访问性与视觉约束

- Tab、邮件行、类别导航、Toggle、分页和抽屉均支持键盘操作和可见焦点；
- Toggle 具备名称、当前状态、禁用原因和确认文案；红点不能成为唯一状态表达；
- 表格和图表提供文字等价信息，颜色不能是唯一通过/失败信号；
- 长主题、长地址、中英文混排和缺失字段不得破坏行高或遮挡操作；
- 不使用营销式 Hero、嵌套卡片或装饰性大面积渐变；
- 继续复用现有主题 token，并验证浅色、窄屏和常见桌面宽度。

## 9. 测试与验收

### 9.1 前端自动测试

- `学习` 文案全部变为 `模型训练`；
- 已处理和待反馈一封一行，分页、页大小和选中项与 URL 同步；
- 打开、切换和关闭详情抽屉时正文请求、取消请求和焦点恢复正确；
- 待反馈成功后自动选择下一封，失败时保留当前状态；
- 类别配置只显示当前类别集合，三段描述可保存并显示新版本；
- `junk`、important 固定规则只读，`subscription`、`other` 不可选择；
- 三种运行状态、红点、Toggle 禁用/启用/打开状态正确；
- 切换失败后 Toggle 回滚到服务器状态；
- 趋势图对不可比较版本断开，不把缺失数据显示为 0 或 100%；
- Registry 单版本异常不会让整个页面崩溃。

### 9.2 后端与契约测试

- 分页元数据和详情正文边界正确，列表响应不携带完整正文；
- 描述字段和版本保存、读取、并发冲突与历史追溯正确；
- 四项可配置门槛及不可配置完整性条件共同决定 `promotion_eligible`；
- 低于任一门槛、类别缺样本、Registry 异常或 artifact 校验失败时不能启用切换；
- 模式切换幂等、持久化并能 readback；
- 切回 Agent 主分类不删除模型或历史证据；
- 不产生 Email 回复，不改变退订或 Audit 生命周期。

### 9.3 浏览器验收

在真实本地数据上逐项检查四个 Tab：

- 1280px 及以上桌面宽度每页可快速扫描，邮件行稳定且正文不撑高；
- 760px 以下不出现逐字竖排、遮挡或无法关闭的抽屉；
- 处理和待反馈分页可以前后切换并保留 URL 状态；
- 类型描述、文件夹映射和系统固定规则与后端事实一致；
- 模型模式、门槛、红点、Toggle、趋势、版本表和详情与 API readback 一致；
- 页面刷新后不会把影子模式误显示为主模型。

## 10. 实施边界与顺序

后续实施计划应拆成可独立测试和提交的阶段：

1. Email Console API 契约和模型晋升状态；
2. 共用高密度邮件列表、分页和详情抽屉；
3. 三段式类别描述和 folder binding 配置；
4. 模型训练总览、门槛、红点和 Toggle；
5. 趋势图、版本表和详情抽屉；
6. 全量前后端测试、真实浏览器验证、静态资源重建和本地服务重载。

实现不得混入新的 Audit、安全审批、回复授权或退订生命周期变化。运行代码完成并提交后，
必须按仓库约定重启 `com.ceo-agent-service.main`，验证新进程、Email backlog、失败项和真实
浏览器页面，才能宣称交付完成。
