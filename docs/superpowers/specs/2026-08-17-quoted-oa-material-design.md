# 群聊引用 OA 审批卡片材料绑定设计

## 背景与目标

钉钉群聊消息可能只包含简短指令，真正的 OA 审批链接位于被引用的审批卡片中。当前直接 Agent 路径会把引用内容提供给 Agent，但 OA 材料提取只检查消息正文，因此 Agent 看得到自然语言引用，却拿不到经过验证的 `process_instance_id`、`task_id` 和标准读取命令。

本次改动把引用卡片中的 OA 链接绑定为当前 Agent 架构可消费的透明材料。它只补齐输入材料，不自动执行审批、不绕过 Agent 判断，也不恢复已经移除的 Universal Consumer 架构。

## 范围

- 支持群聊消息正文没有 OA 链接、但 `trigger.quoted_content` 含有效 OA 审批链接的场景。
- 复用现有 OA URL 解析、标识符校验和 `dingtalk_oa` 材料格式。
- 保持消息正文或已持久化任务材料中的 OA 链接优先。
- 保持 Agent 当前的读取、判断、工具调用和审计链路不变。

不在范围内：自动批准或拒绝审批、从普通文字猜测审批标识、恢复旧 Consumer 路由、改变 DWS 权限或审批写入策略。

## 数据流与优先级

```text
钉钉群聊触发
  ├─ 消息正文 / 已持久化任务材料存在 OA 链接
  │    └─ 沿用现有 dingtalk_oa 材料
  └─ 不存在 OA 链接
       └─ 检查 trigger.quoted_content
            ├─ 有效 OA 链接 → 解析并生成 dingtalk_oa 材料
            └─ 无效或不存在 → 不生成 OA 材料

dingtalk_oa 材料
  └─ 进入现有 Agent prompt/runtime
       └─ Agent 先读取审批材料，再自主决定是否需要执行动作
```

来源优先级固定为：现有持久化 OA 材料或消息正文，其次才是引用内容。引用内容只能填补缺失，不能覆盖正文中已经明确绑定的审批实例，以避免同一消息出现两个卡片时静默换绑。

## 材料契约

从引用内容解析成功后，生成与现有正文 OA 链接相同的 `dingtalk_oa` 材料，至少包含：

- 原始且可追溯的 OA URL；
- 精确解析并验证过的 `process_instance_id`；
- 精确解析并验证过的 `task_id`；
- 现有的审批详情与任务列表读取命令。

材料应明确标注来源为引用内容，便于白盒诊断，但不得把引用卡片描述当作审批事实。审批状态、表单字段、处理记录和评论仍必须通过既有 DWS 读取命令获取。

## 安全与执行边界

该功能不是新的审批授权层。它不会因识别到 OA 链接而自动调用同意、拒绝、转交或评论接口，也不会创建独立后台任务。现有 Agent runtime、工具能力和审计记录继续决定并记录实际动作。

解析失败采用保守降级：不生成 OA 材料，保留原始引用上下文供 Agent 解释；不得伪造空标识符、部分绑定或把失败解析成另一条审批。若正文和引用各自包含不同的有效审批链接，正文绑定保持权威，引用链接仅作为上下文存在。

## 实现位置

改动应落在当前 `app/worker.py` 的 OA 材料构建边界，并复用现有 URL 提取与材料渲染函数。若提取函数目前只能接收正文，可将“按来源顺序选择 OA URL”提炼为一个小型纯函数；不引入新的路由、存储表或抽象层。

文档同步更新当前审批可靠性说明，明确引用卡片只用于补齐材料，实际审批仍由 Agent 在读取完整事实后决定。

## 测试与验收

实现按测试驱动方式完成，至少覆盖：

1. 群聊消息正文无 OA 链接、引用审批卡片含有效链接时，生成一个 `dingtalk_oa` 材料。
2. 材料包含引用链接中精确的 `process_instance_id`、`task_id`、OA URL 和现有读取命令。
3. 构建材料不会调用任何审批写入动作，也不会自动得出同意或拒绝结论。
4. 正文已有 OA 链接且引用中还有另一条链接时，正文链接保持优先，不发生静默换绑。
5. 引用内容缺失、格式错误或缺少必需标识符时，不生成伪造或部分 OA 材料，现有非 OA Agent 流程继续工作。
6. 既有正文 OA 链接、直接消息、任务恢复和其他材料测试全部保持通过。

完成后运行相关 worker/Agent 回归测试、完整后端测试和前端测试；运行时代码提交后按项目规则重启 launchd 服务，并验证新进程与未解决积压。
