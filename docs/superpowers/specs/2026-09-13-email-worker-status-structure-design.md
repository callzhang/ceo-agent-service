# Email Worker 状态结构设计

**日期：** 2026-09-13
**状态：** 已确认，待实施

## 问题与证据

Settings → Status 当前把 `service_state` 中所有 `email_worker_health:*` 行平铺成一张 “Email worker” 表。线上快照因此显示 11 行，但操作系统实际只有一个 `python -m app.cli email-worker` 进程；该进程只启动三个常驻线程：扫描与确定性动作、Agent Consumer、训练维护。

现有 11 行混合了四种不同事物：一个进程、一个邮箱账号、三个常驻循环，以及分类器、provider action、训练观察、启动配置和历史迁移等内部检查。进程记录里的 `components=2` 又只表示“启动就绪必须完成的两个循环”，与三个实际循环含义不同。最后，状态接口读取所有历史键且没有区分进程实例，所以前一次启动留下的 `ready` 行会继续出现在当前页面。

## 已选方案

健康写入为每次 Email worker 启动生成一个 `instance_id`，并自动附加到该进程产生的每条健康记录。进程摘要记录从实际启动线程派生的 `runtime_loop_scopes`，并分别记录：

- `runtime_loops`：实际常驻循环数量；
- `readiness_ready`：已通过启动门槛的循环数量；
- `readiness_total`：启动门槛要求的循环数量。

状态快照以当前 `process:email-worker` 的 `instance_id` 为边界，只投影同一实例的记录；不迁移、不兼容展示旧实例数据。记录分组不依赖前端硬编码名称：进程记录是摘要，`account:*` 是账号，进程摘要声明的 scopes 是运行循环，其余同实例记录是内部检查。

接口由一张平铺表改为结构化对象：

```text
email
├── process
├── runtime_loops[]
├── accounts[]
└── checks[]
```

页面展示一个 Email Worker 概览、运行循环表、账号表和内部检查折叠区。健康内部检查默认折叠；任一内部检查不是 `ready` 时自动展开。状态、错误码、计数和更新时间仍由后端提供，页面不推断业务状态。

## 备选方案

1. 仅在前端按 scope 名称分组。改动最小，但会把运行模型硬编码进 React，仍无法可靠排除旧进程记录，因此不采用。
2. 启动时删除所有旧健康键。页面会变干净，但删除不是进程归属证明；并发或异常启动时可能误删仍有价值的诊断记录，因此不采用。
3. 为每次启动标记实例并由后端结构化投影。数据归属明确，页面契约稳定，新增内部检查不会增加“worker 数量”，因此采用。

## 边界

本次不改变邮箱扫描频率、分类、provider action、Agent Consumer、训练、重试、外部动作或启动门槛，只改变健康记录元数据、状态 API 和 Status 页面。旧实例健康数据继续保留在 `service_state` 供本地诊断，但不再作为当前状态返回。

## 验收

- 一个正常 Email worker 显示为一个进程、三个运行循环、实际账号数，以及一个可折叠的内部检查区。
- 页面不再把内部检查称为 worker。
- 摘要同时显示“运行循环 3”和“启动必需 2/2”，不再用一个 `components` 数字承载两种含义。
- 当前进程实例之外的健康记录不出现在 API 或页面。
- 缺少进程记录时 Email 状态为 unavailable，分组为空。
- 后端契约、前端运行时校验、页面渲染和窄屏布局均有回归覆盖。
