## Current call paths and meanings

The direct retry release path is CLI → `email_action_reconcile.release_source_verified_retry` → `EmailStore.release_source_verified_direct_action`. It verifies one source read-only, then stores the next-attempt authorization, source digest and exact account snapshot. Polling/specific claim paths compare current account configuration; completion and stale-processing recovery consume the allowance without renewing it. `source_readback_digest` is retained proof; the worker predicates read the key/configuration snapshot rather than re-verifying a historical digest. The existing Email50→51 release rollback refuses a nonempty authorization relation, so that old publication inverse is not proof of a future field transition.

Human feedback runs through the Console feedback endpoint → classifier learning (when configured) → `email_pipeline.apply_human_confirmation` → `_apply_human_classification`. Initial confirmation requires NULL expected plan; correction requires exact current plan. Replaying the same request checks the prior intent and returns the original result plan/time. The existing training-label wrapper creates an actionless plan; no external app caller to that wrapper was found in the exact-symbol search. These six fields are business decisions, idempotency and result lineage, rather than a raw copied request body.

The surviving `EmailReplyDelivery.deliver` module reads authorization/claim/receipt, acquires an owner-fenced claim, uses its actual account snapshot, and persists matched Sent evidence. Possible dispatch and terminated-owner recovery become `uncertain`; explicitly undispatched release becomes `retryable`; matching persisted Sent evidence completes the claim. The full account snapshot is a configuration input used by this path, with credential references rather than credential values. The receipt contains actual Sent folder/UIDVALIDITY/UID and optional SMTP acceptance ID; it is separate from copied email/reply/trajectory text. Receipt replay permits enriching only an empty SMTP acceptance ID and preserves other evidence.

Current docs explicitly disable SMTP/auto_reply and category-config validation rejects `auto_reply`. The methods and delivery implementation still exist; an exact app symbol scan found no `EmailReplyDelivery` construction or external caller to terminated-owner recovery. This source inventory maps their source contracts and does not infer a live send path from API existence. Source method calls inside the module and the durable validator remain in the JSON.

Context source and worker consume safe receipt summaries via `list_email_context_receipts`; `list_email_classification_observability` projects a safe classification result view. They do not expose provider targets, raw receipt payloads or task/body inputs. Source paths below are exact function starting lines; field checks/writer mutations are defined by current source and the full captured DDL. DAO readers may load a complete row and then project only selected keys: for example, source_readback_digest is loaded by the retry durable-state scan but not semantically re-verified there, and applied_at is loaded by feedback durable validation while its meaningful replay use is _feedback_application.
