# 周报项目风险进入「需关注」：第一版设计

日期：2026-10-01。状态：待 Derek 审阅。本文是设计，不表示代码、数据回放或生产服务已经变更。

## 目标与边界

修复已确认的断点：项目管理部 W39 周报的「手头项目」列明中汽创智回款/现金流风险、岚图结算争议，Task Agent 却只从「下周工作重点」生成候选 Task，没有把这些 Task 关联到周报中的项目，也没有提出任何关注事项。第一版应让同一份周报内分散的项目行、风险影响和后续动作能够共同支持判断；关注不等于要求 Derek 亲自介入。

第一版只处理有独立项目登记依据、且能关联真实 Task 的周报项目风险。Agent 可以综合同一份周报的不同章节推断重大性，但必须分别指出原文事实与推断结论；单独的「⚠️有风险」标签、日期临近或一般进展不能自动进入关注。W39 的中汽创智与岚图是定点验收案例。NPS 等无正式项目的跨部门事项、跨会议/聊天的综合推断、近四周批量回放和历史项目别名合并留待后续；本版不把它们伪装成 Project 或造出没有来源的 Task。

## 数据流与最小改动

保留唯一的 `scan evidence → Task Agent → update Tasks` 路径和现有周报扫描器。周报输入向 Task Agent 明确呈现独立项目登记行；相关 Task 决定仍引用自己的行动原句，`project_proposal` 另附登记表中的精确项目行。服务验证该行确实位于原周报的项目登记区域、标题一致，再登记/复用正式 Project 并关联 Task。项目和任务名称只是线索，不凭客户简称自动合并既有项目。

关注提议引用同一份周报中说明经营影响的精确原句，允许该句与 Task 行位于不同章节。服务在整份当前周报正文而不是单条 `source_excerpt` 中核验引文；先完成 Task 与 Project 关联，再用项目标题解析本轮刚取得的 anchor ID，Agent 不需猜尚未创建的数字 ID。每个项目最多提出一条当前关注，持久化身份以已确认的项目 anchor 为准，跨周更新同一卡片；相关的开放 Task 作为卡片证据。`watch` 类可以明确写「当前无需你处理」和下一次应观察的结果，不被错误表达成「需介入」。

本版沿用现有 Task Agent 运行与关注投影边界，不加入第二个 Agent、额外定时维护或按风险标签直投。投影成功与否必须有可读回执：每份周报按输入 ID/运行 ID 记录发现的项目行数、Task 决定数、已关联项目数、关注提议数、实际入库数，以及未入库的原因。日志只存计数、ID 和简短原因，不复制周报全文。运行完成但关注投影失败时不能在诊断中显示为「已生成关注」；运维可以依据该输入 ID 定点复查和重试。

## 验收与上线

先写会在现状下失败的回归测试：同一周报内项目行与行动行分离、风险影响在第三处时，项目仍被关联，`watch` 关注落库；只写「有风险」却无实质影响时不落库；新项目无预存 anchor ID 时可在同轮完成；候选 Task 有确认的项目关联时可支持关注；同一项目多条行动不产生重复卡片；投影失败留下明确诊断。用真实 W39 文本的脱敏固定样本检验中汽创智、岚图两项，同时确认 NPS 不被误注册为 Project。

代码和针对性测试通过后，同步更新描述 Task/Project/Attention 行为的架构与运行文档，按现有生产部署流程上线。先在生产数据库副本上对 W39 输入做定点回放，核对 Task/Project 去重及预期两张关注卡；再备份生产库，只重排这一条已完成的周报输入，交给原有处理队列执行。验收分别读取 Task Agent 决定、项目关联、关注表和控制台 API；若副本回放出现重复 Task/Project 或额外关注，停止生产回放，先修正身份/判断逻辑。第一版验收不以四周历史覆盖率或 NPS 展示为门槛。
