# Workbench Runtime Auto Mode Design

## Goal

Make the local, single-user Agent Workbench a white-box runtime console instead of a second permission system.

## Product boundary

The Workbench runs for one CEO under that person's macOS account. It coordinates the selected Agent runtime, persists state, streams progress, and renders the runtime's evidence. It does not classify commands as safe or unsafe, inject a separate confirmation tool, mask local paths, or reject/redact provider output because it resembles a credential.

Codex runs with its non-interactive approval-and-sandbox bypass so local commands and MCP tools do not pause behind Codex approval review. Claude and Pi adapters must map the same Workbench contract to their corresponding automatic execution modes when those adapters are added.

## Runtime flow

1. The executor claims a persisted turn with its existing lease.
2. `CodexRuntime` starts native Codex with the user's own configuration, skills, plugins, MCP servers, and authenticated local CLI state.
3. Workbench does not add `workbench_confirmation`, special risk instructions, or an additional allowlist.
4. Native command and MCP events are normalized only for JSON compatibility and correlation. Their command, cwd, arguments, result, output, provider item, and assistant text are persisted and rendered without semantic redaction.
5. Runtime failure, stop, timeout, lease loss, and process cleanup keep their existing authoritative state transitions.

## Removed behavior

- No new `confirmation_required` event is generated by the Codex adapter.
- No Workbench confirmation MCP is injected into Codex.
- No Workbench developer prompt instructs the Agent to propose reviewed actions.
- No credential-shaped text causes a Workbench turn to fail or a tool payload to be replaced with `[REDACTED]`.
- No frontend display helper masks credential-shaped text in historical cards or execution summaries.

Existing persisted confirmation records and API shapes remain readable so old timelines are not corrupted. They are historical compatibility data, not part of the new execution path.

## Preserved correctness guarantees

- one active executor lease per turn;
- idempotent stop and terminal transitions;
- child-process termination and watchdog cleanup;
- crash recovery and no-progress detection;
- exactly-once persistence transactions and SSE event ordering;
- attachment and artifact storage integrity.

These mechanisms prevent duplicate work and corrupt state; they do not judge whether the CEO is allowed to use a local tool.

## Verification

- Command construction proves bypass mode is present and confirmation overlays/instructions are absent.
- A provider event named like the former confirmation tool remains a normal MCP tool event and cannot pause the turn.
- Credential-shaped assistant, command, MCP result, path, and provider data survive normalization unchanged.
- Frontend tool cards render the same values unchanged.
- Existing executor stop, recovery, lease, store, API, SSE, frontend, and production build suites remain green.
- Production acceptance runs a harmless local command without a confirmation card, then verifies terminal state and live queue health.
