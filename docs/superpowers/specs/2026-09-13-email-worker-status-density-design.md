# Email Worker 状态页信息密度设计

**日期：** 2026-09-13  
**状态：** 已确认，待实施

## 问题

Settings → Status 已经把 Email worker 区分为一个进程、三个运行循环、邮箱账号和内部检查，但正常状态仍无条件展示三个运行循环、一张账号表和 `Internal checks (N)`。这些记录不是额外 worker，然而页面把正常诊断明细放在主信息层，仍会让人产生“为什么有这么多 worker”的印象。

线上确认的正常实例包含一个 Email worker 进程、三个运行循环、一个账号和五个内部检查。所有项目都为 `ready` 时，运维结论只有“Email worker 正常”，逐项列表没有额外决策价值。

## 设计原则

状态页采用 exception-first 展示：正常状态回答“是否正常、规模多大、何时更新”，异常状态回答“哪里异常、为什么、何时发生”。完整健康数据继续由 API 返回，前端只改变展示层级，不删除诊断数据，也不改变 worker、扫描、分类、训练或邮箱动作。

## 正常状态

当进程、所有运行循环、所有账号和所有内部检查均为 `ready` 时，Email worker 区域只显示一个摘要：

```text
Email worker    就绪    1 个账号 · 3 个运行循环 · 启动 2/2    更新时间
```

正常状态下不渲染：

- 运行循环明细表；
- 账号明细表；
- `Internal checks (N)` 或任何健康检查数量；
- 全部为 `ready` 的诊断行。

摘要保留进程状态、账号数、运行循环数、启动就绪数和更新时间。这里的运行循环数量是规模信息，不把循环称为 worker。

## 异常状态

异常集合由以下记录合并产生：

- 进程状态不是 `ready`；
- 运行循环状态不是 `ready`；
- 账号状态不是 `ready`；
- 内部检查状态不是 `ready`。

当异常集合非空时，摘要仍保留，并在其下直接显示“异常项”表。表格只包含异常记录，不夹带正常记录；无需用户先展开 disclosure。每行显示类型、名称、状态、脱敏详情和更新时间。

进程异常作为一个显式异常项展示。若进程记录缺失，则使用 Email 顶层状态生成唯一的进程异常项，不重复报告同一个缺失问题。`starting`、`degraded`、`unavailable` 等所有非 `ready` 状态都属于异常，不在前端维护额外状态白名单。

## 数据与组件边界

- 后端 Status API 契约保持不变，继续返回 `process`、`runtime_loops`、`accounts` 和 `checks`。
- 前端从这些分组派生异常集合；不按具体 scope 名称硬编码检查项。
- 名称继续移除 `component:`、`account:` 等技术前缀；异常行额外标注“进程 / 运行循环 / 账号 / 内部检查”类型。
- 详情继续使用现有的有界字段：`error_code`、失败数、持久化数、任务数、隔离数、替代数和未解决数；不显示原始 payload。
- 不增加新的展开开关，不持久化 UI 状态。

## 备选方案

1. **只折叠内部检查。** 改动最小，但三个运行循环和账号表仍长期占据页面，不能解决信息密度问题。
2. **删除所有诊断明细。** 页面最简，但发生故障时无法定位具体循环、账号或检查，降低运维价值。
3. **正常摘要、异常明细。** 正常时只有一个结论，异常时保留精确定位能力，因此采用。

## 验收标准

- 全部健康时，Email worker 区域只有一个摘要，不出现运行循环表、账号表、内部检查标题或任何健康明细名称。
- 任一运行循环异常时，只显示该异常循环，不显示其他健康循环、账号或检查。
- 任一账号或内部检查异常时，只显示对应异常项，并显示已有的安全详情与更新时间。
- 进程异常或缺失时只出现一个进程异常项，不重复。
- 页面仍明确表示只有一个 Email worker，并保留账号数、运行循环数和启动 `ready/total`。
- 桌面与 390 px 窄屏均无水平溢出、裁切或不可读字段。
- 前端单元测试覆盖全健康、循环异常、账号异常、检查异常和进程缺失；真实浏览器覆盖正常与异常两种视觉状态。

## 非目标

- 不改变 Email worker 的进程数、线程数、启动门槛或运行周期；
- 不改变健康记录写入、实例隔离或 API schema；
- 不增加主动 API 探测或合成健康记录；
- 不处理 Status 页其他模块的信息密度。
