# 以 Project 为上下文中心的工作跟踪设计

日期：2026-10-04。

状态：**Derek 已于 2026-10-04 以“OK 好的，继续”确认整体设计，进入实施计划阶段。** 本文响应“对比原来的 Task→Project 与现在的 Project→Task，并根据讨论设计”。批准设计不代表完成实现或发布；行为改动时须在同一提交中同步契约、Skill、架构和运行文档。

## 1. 结论与适用边界

推荐：**信息先汇入真实 Project 的上下文，再形成项目判断、更新已有 Task，以及推导建议 Task；真实 Task 不以 Project 已识别为存在前提。**

Project 是“这件业务要达成什么、现在怎么样、谁总负责、各人负责什么”的长期记录。Task 是具体可执行、可完成的事项，既可能来自人的明确安排，也可能是 Agent 根据项目情况提出的建议。两种来源必须看得出来，不能把建议显示为已指派或已承诺。

这不是两条并行管线，也不新增 Project Agent、Completion Agent。仍由一个共享 session 的 Task Agent 处理新信息；改变的是其上下文组织与输出对象，而不是增加第二个业务判断者。

当项目归属未知时，明确的真实任务照常记录，项目关联可以暂缺；本来就不属于项目的独立任务保持独立。不得为了套用 Project-first 而制造项目。

## 2. 已确认要求与本次确认的设计改变

### 已确认

- 综合会议、管理/部门/项目周报、聊天及其他相关来源；周报不是唯一信息来源。真实项目定义优先依据会议及权威业务记录，聊天补充近况。
- 与主营业务、公司业务主线无关的零碎小事不进入默认关注；不会因小任务多就自动聚类成正式项目。
- Agent 可以根据项目情况和人员职责推导需要做的事及合适的人选，不要求本次原文必须同时说出任务和人名。
- 推导的任务和负责人建议**先展示，不直接派发**。
- Project 要有明确的负责人和负责事项字段；一个项目只有一个总负责人，其他参与者分别负责不同事项，不存在“共同总负责”。
- 需关注不等于需要 CEO 介入；区分知晓、观察、决策与推动。
- 先简单做、做好可观测，再根据真实效果改进；保持一个 Task Agent，不恢复周期性 Task maintenance/completion 业务判断。

### 本次整体设计确认的改变

- Project 上下文作为独立业务记录更新，不再以某条 Task 决定作为项目登记、项目事实或人员分工的唯一入口。
- Project 可以在没有关联 Task 时，根据明确项目身份及相关原始证据产生需关注判断与卡片。没有 Task 不是“证据不足”的充分理由。
- 建议任务与已有真实任务在同一个项目下展示，但明确标记来源和状态，建议不进入已指派、已接受及已承诺统计。
- 原文共享存储和组织引用；项目摘要、项目判断与任务信息都可回到原始来源，摘要不是新的事实凭证。

其中第二项是相对 2026-10-02/03 已批准关注设计的实质变化，已随本次设计获得确认；不能将它描述为原有实现已经支持的行为。

## 3. 原设计解决了什么，现在缺什么

2026-09-22 的 Task-first 设计针对的是实体混淆：原有 work_projects 混入项目、任务、TODO、阶段节点和临时事项。先发现真实任务，再匹配真实项目，避免为了保存一条任务而创建一个“项目”。这项成果应保留。

Task-first 的概念本身不禁止多来源推断，也不必然导致原文重复；这些取决于上下文和数据组织方式。当前受限的是具体实现：

- `BusinessProject` 核心记录主要保存身份、标题和登记来源，没有独立的总负责人、分工与项目近况字段。
- 项目页面已有部分负责人/事项等展示，但主要从关联 Task 的报告证据投影出来，不等于 Project 已有独立的持续上下文。
- 项目登记提案嵌在 Task 决定内；2026-10-02/03 关注路径虽然允许 Task 字段不变，仍依赖正式 Project 与真实 Task 的确认关联。
- 因而“项目出现风险，但原文没有新行动项”容易被迫寻找一条 Task 作为挂载点；真正重要的项目事实不能自然地独立沉淀。

冻结的 W39 回放还暴露了首轮遗漏一个项目判断、普通进展被判证据不足等业务问题。输入中重复证据较多是已观察事实，但“重复输入导致这些漏判”尚未证明；本设计不能据此保证改为 Project-first 就一定不漏判。

## 4. 三种取舍

| 维度 | 保持 Task-first，完善上下文 | 严格 Project-first，所有 Task 必须归项目 | 推荐：Project 为中心，允许独立/未关联 Task |
| --- | --- | --- | --- |
| 起点 | 发现具体行动，再关联项目 | 先完整识别项目，再产生任务 | 先理解相关真实项目；明确任务同时保留 |
| 明确的人类安排 | 直接、易于追溯 | 项目不清可能阻塞记录 | 保留直接记录与更新能力 |
| 无行动项的经营信息 | 可以支持，但需补独立项目上下文 | 自然进入项目判断 | 自然进入项目判断，不强造任务 |
| 按职责推导下一步 | 也能做，但需补项目整体视角 | 适合 | 适合，并区分建议与已安排 |
| 项目识别错误的影响 | 通常先影响归类，任务仍存在 | 可能污染整组任务，甚至丢工作 | 仍有传播风险；不确定关联不强行落定 |
| 冷启动/独立事项 | 较好 | 较差，容易再造假项目 | 可渐进建立项目上下文 |
| 原文重复引用 | 可以单独修复 | 不自动解决 | 通过共享来源和引用明确解决 |
| 本次改造成本 | 最低，但只解决部分目标 | 最大，改变所有任务入口 | 中等偏大，保留任务生命周期和来源扫描 |

如果目标只是少重复、降低上下文体积，保持 Task-first 并修复来源组织更便宜，不必为了压缩提示词重构项目模型。

当前目标已经包括“理解项目整体、记住分工、推导下一步并说明为什么关注”，所以推荐第三种。它的主线是 Project→Task，但保留原设计中“真实 Task 可独立存在”的正确边界。代价是必须维护项目身份、当前事实与职责的准确性，而不能只增加一个项目摘要文本框。

## 5. 对象与字段

### 5.1 共享来源

原始会议、周报、消息、邮件等以可识别的来源和版本保存。项目和任务使用来源引用及相关段落，不各自复制整份正文。

- 一份周报可以支持多个 Project，一个 Project 可以关联多份周报和会议；来源与项目不是排他的从属关系。
- 相同正文在本轮输入中按原始来源版本组织一次，项目/任务通过引用访问。不同 Signal 指向同一来源时，不按 Signal 数量重复塞全文。
- 新版本、不同日期、不同作者的相似说法不是同一证据；不能因文本相似就抹去变化、冲突或来源身份。
- Project 摘要用于导航和当前状态理解；决定状态、分工或风险时，能够读到其引用的原文。摘要不作为证明自己的新来源。
- 对长文按来源已有章节/段落提供可追溯内容，同一正文不必永远全量送入。记录本轮实际读取与未读取范围；截断不能声称已经完整读过。

这解决的是共同背景重复，不限制同一句原文合法支持两个不同判断。

### 5.2 Project

Project 对齐真实业务中的项目及其目标、范围；部门、客户名字、相似主题或任务集合都不自动成为 Project。沿用真实项目登记依据，不能通过聚类或名称相似度直接建立正式身份。

项目发现仍由同一个 Agent 从上下文中提取，不要求人工先建立完整项目表。会议或权威业务记录明确了一个尚未登记的真实项目时，可以独立提出登记/更新，不再要求同时提出一条 Task；只有聊天线索或归属不明时，保留线索而非假定正式身份。

| 字段 | 含义与展示 |
| --- | --- |
| 项目身份、名称 | 稳定身份与来源中的正式名称，不用 Task 标题代替 |
| 目标与范围 | 要交付/达成什么，哪些事情属于这个项目 |
| 总负责人 | 一个人；现实中唯一不代表系统已经知道，未知显示“待明确” |
| 总负责事项 | 该人对项目整体负责的结果/范围，不能只有人名 |
| 人员分工 | 多条“人员＋负责事项＋依据”；不是多个总负责人 |
| 当前情况 | 进展、关键日期/节点、阻碍与变化，分别保留来源与时间 |
| 项目判断 | 是否需关注、经营影响、事实与推断、需要什么动作或当前无需动作 |
| 相关任务与建议 | 引用已有 Task 及展示中的建议，不复制任务状态 |

#### 客户关联（2026-10-06 确认的补充设计）

客户是独立于 Project 名称的可选关联。Project 可以关联一个从 CRM 解析的客户实体；该关联使用 CRM 提供的稳定客户 ID，页面展示名称从 CRM 客户记录读取，不把客户名拼进项目名。Project 可以没有客户关联，因为并非每个内部项目都是对外客户项目。按客户汇总时，只汇总明确关联到该 CRM 客户的 Projects。

Task Agent 不得通过项目名、聊天提及或相似名称猜测并写入客户关联。若 CRM 没有匹配记录，或候选不唯一，关联保持为空并将线索留给人工确认；Task Agent 不创建或修改 CRM 客户记录。客户关联不改变 Project 的正式身份，也不自动表示该项目是对外交付项目。

验收例子：

- “甲客户一期交付”在 CRM 中唯一解析到客户 ID `crm-customer-123`：Project 名称仍为“甲客户一期交付”，客户字段引用该 ID，展示名从 CRM 读出。
- “算法平台重构”是内部项目：客户字段为空，项目仍可正常登记、关联任务并参与项目关注。
- “甲客户二期”在 CRM 中有两个同名客户候选：不任意选一个，客户字段保持为空。

已建立的负责人和分工由来源支撑。新信息明确变更时更新当前值并保留历史；来源冲突时说明冲突，不能简单选择最新一段文字或把两人并列成总负责人。总负责人空缺不阻止保存其他项目事实。

Agent 可以基于已有项目分工或有依据的组织/岗位职责，推导某条建议任务适合交给谁；这不等于改写项目正式分工。只有建议人选时标记为建议，不能作为下一轮“此人已承担该职责”的事实。

### 5.3 Task 与建议

继续使用一个任务体系表达具体事项，不再建第二份独立任务账本。区分来源类型、展示状态与人的承诺状态：

- **已安排的任务**：来自人的指派、承诺、会议行动项或明确外部任务。保留原任务身份、完成状态、实际指派人、负责人、指派/接受证据。
- **Agent 建议**：由项目目标、风险、分工推导，显示“建议做什么、建议由谁做、为什么、依据什么”。即使建议人选十分确定，也不是“已指派”或“对方已接受”。
- **来源中的待明确事项**：原文提到了动作但信息不足，说明缺什么；不与 Agent 建议混为同一解释，也不强行提升为正式任务。

推导前读取项目内已有任务和建议。已有同一交付事项时补充证据或更新，不重建一条；不同交付物即使属于同一项目也不能合并。后续人类指派证据与某建议对应时，沿用同一事项的身份或可追溯关联，不同时留下两条活跃副本。

日期继续区分创建日期、分配日期、请求截止、承诺截止和建议日期；没有证据不编造 DDL。建议任务不会创建钉钉 TODO、发送通知或催办，也不自动产生人的承诺。本设计不新增派发或确认流程。

## 6. 一次处理的工作方式

```text
新来源信息 + 相关原始历史依据
                  ↓
同一个 Task Agent：理解来源、匹配真实项目、读取现有分工和任务
                  ↓
          更新项目事实和当前判断
                  ├─ 更新/记录明确的真实 Task
                  ├─ 展示按项目情况与职责推导的 Task 建议
                  └─ 更新项目“需关注”（允许没有 Task）

项目归属未知的明确 Task：正常保留，关联待明确，不强建 Project。
```

这是逻辑组织顺序，不要求每一步另起一次模型调用，不要求先跑全公司项目发现再处理一条消息。一次来源可以产生零到多个 Project 更新、Task 决定或建议；只处理本次新信息影响的对象。

需要修改当前输出契约：项目更新和项目判断成为同一次返回中的独立部分，不再寄生于某条 Task 决定；Task 决定引用相关项目，或明确保持无项目。由现有服务操作保存各对象并读回实际结果，不新加业务编排 Agent 或隐藏补卡路径。

依然只在新信息进入时更新，不周期性重问所有未完成任务。钉钉用户直接完成 TODO 的确定性反馈路径保留；它只关闭对应 Task，不自动证明整个项目、风险或其他任务已完成。共享 session 负责连续推理，持久化项目/任务及原文负责事实；不能依赖 session compact 后仍保留每一处细节。

## 7. 需关注与页面表达

项目出现实质经营风险、重要变化或决策需要时，可以需关注，即使没有人提出具体行动项。项目身份与风险证据仍要成立，普通正常进展不能因为“有项目”就变成关注。

例如项目付款节奏改变、可能影响现金安排，但尚无催款任务：可显示“持续观察／付款时间不确定，当前无需 CEO 动作”。无需先伪造“催款”任务才能展示。

关注判断与任务建议是两个结果：需关注可以没有建议；提出建议也不必然值得 CEO 关注。任务完成不自动消除项目风险；本轮“不产生新的关注”也不自动关闭旧卡片，风险解决须有对应证据。延续同项目的已有折叠方式，保留不同问题的具体事实与关联任务，不因每条 Task 重复展示同一项目风险。

先使用现有需关注、项目、任务页面，不新建管理模块：

- 项目列表直接显示项目名、唯一总负责人、总体负责事项、当前情况、关注原因及更新时间。
- 项目详情先展示整体情况和人员分工，再展示已有任务与 Agent 建议，最后是可追溯来源。
- 任务列表保留类似 email 列表的密度，直接看到事项、项目、负责人或“建议负责人”、状态、明确类型的日期；不必逐条点开才知道重要信息。
- 不把项目整体状态完全折算成“完成了多少 Task”；那只是执行数据，不是经营结论。

## 8. 贯穿例子（假设案例，不是真实人员或项目事实）

项目为“甲客户一期交付”，已有项目记录：张三总负责交付和验收，李四负责验收材料，王五负责商务回款。

本次输入包含：

1. 会议：“李四周五补齐验收材料。”
2. 周报：“客户尚未给出付款日期。”
3. 聊天：“对方希望等验收材料齐了再走付款。”

只按原来的任务中心入口，第一项很容易成为真实 Task；第二、三项需要另外汇总理解，不能仅从 Task 是否逾期推出项目的回款状态。

推荐设计的结果：

- Project 事实：材料待补；付款日期未确定；付款流程与材料有关。三个来源分别引用，不能把“有关”升级成已确定的延期金额或日期。
- Project 判断：回款时间存在不确定性，是否达到需关注由业务影响判断；若影响本期现金安排可持续观察，不能仅因涉及付款就自动升级。
- 已安排 Task：李四补齐材料，请求截止为周五；没有接受证据就不写“李四已承诺周五”。
- Agent 建议：王五确认付款前置条件及预计排期。依据是既有商务职责和新信息，不要求本次消息点名王五；显示为建议，不产生指派记录或通知。
- 张三仍是唯一总负责人；李四、王五不是另外两个项目总负责人。

若没有第一项，仍可形成项目情况、判断和建议；若第一项存在但暂时无法确定哪个项目，李四的真实任务仍应保留。

## 9. 简单、可观测的第一版

第一版只做三个相互配合的改动：共享来源组织；独立 Project 上下文（含单一总负责和人员分工）；同一 Agent 输出项目判断、真实任务更新和展示型建议。沿用现有存储、来源扫描、共享 session 和页面，不引入通用知识图谱、组织职责引擎、第二 Agent 或隐藏恢复循环。

沿用运行记录和实际写入回执，能够看到：

- 本次来了哪些来源/版本，读取了哪些范围；Agent 识别了哪些项目，有哪些未能归属。
- 每个已识别项目的判断、依据和缺失信息，哪些当前字段被更新、哪些保持不变。
- 哪些事项是原文明示、哪些是推导建议；建议负责人取自哪条项目分工或岗位职责。
- 是否更新已有 Task/卡片，实际对象是什么；判断完成与写入失败不能混为一谈。
- 上下文体积、独立来源数量和重复正文体积，便于比较改造前后。

“Agent 未识别某个项目”不能仅靠它自己输出的列表证明不存在。固定案例与人工读原文建立预期项目集合，检验遗漏；线上可见的章节和本轮读取范围只提供诊断依据，不冒充完整语义覆盖证明。明确区分正常不关注、证据不足、未判断与应用失败。

## 10. 迁移与取舍成本

1. 保留正式项目、真实任务的身份与历史，不删除或批量重命名。用真实来源补充项目字段，不把某个 Task 的负责人自动抄成项目总负责。
2. 现存真实任务继续存在；新增 Agent 建议不反向改写旧任务的指派/接受状态。旧模糊记录继续保留历史，不因新设计自动展示成候选。
3. 先在同一批冻结资料和数据库副本验证旧/新行为，再安排发布及受控补充已有项目上下文；不把“写了设计”当作批量整理生产数据的授权。
4. 确认新契约后替换 Task 挂载式项目输出，避免长期双写或永久保留两套互相矛盾的规则。代码、prompt、CI Skill、实际加载 Skill 与行为文档须一致发布。

主要成本不在更换箭头，而在项目身份错误可能连带影响任务建议、职责过时可能推荐错人、摘要遗漏可能污染后续判断。因此保留原始依据、未知关联和推断标记是数据模型要求，不额外增加一套审批/审计政策。第一版不以建立完整项目库、完整人员库为前提。

## 11. 验收与设计自检

用相同来源、模型和运行设置比较旧/新版本，并版本化标明改变的产品预期：

1. 明确人类任务在无 Project 时仍能记录；零碎小事不会被包装成正式项目或默认关注。
2. 同一真实项目跨会议、周报、聊天汇总，周报缺席仍可判断；一份来源支持多个项目时不遗漏其余项目。
3. Project 只有一个总负责人；成员有独立负责事项，未知/冲突不显示为多人总负责。
4. 可按既有职责提出未在本次原文点名的人选；建议不显示为实际指派、承诺或截止，不触发外发。
5. 项目无 Task 但风险证据充分时可需关注；普通进展仍不需关注。此项是新的设计预期，不能把旧版本的无 Task 限制偷偷改名为测试错误。
6. 新信息更新已有任务/建议/关注；重复相同来源不新建副本，不制造无变化事件；任务完成不自动关闭项目风险。
7. 共同原文不按每条 Task 重复装载，所有决定仍可回到准确来源/版本/段落；摘要与引用不造成证据自循环。
8. 冻结 W39 案例首轮覆盖人工核对的全部相关项目，包括之前遗漏项；逐项目核对业务判断，正常进展不得无理由判证据不足。不能依靠第二次重跑才算首轮覆盖通过。
9. 看不到关注时，可区分未识别/未判断、正常不关注、缺证据与应用失败；输出通过或测试全绿不等于业务结果正确。

本文自检边界：未引入自动派活、新 Agent、完成检查、后台补卡或额外审批体系；不把 Project-first 宣称为去重或准确性的自动保证；原有要求与本次确认的设计取舍分开。运行服务仍遵循其已部署契约，直至按实施计划完成替换，不能仅凭本文批准改变线上行为。
