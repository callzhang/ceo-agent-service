# 系统任务与审核范围对应

Derek 明确要求：所有系统审核项都必须对应实际系统任务；没有对应系统任务，就不设置该业务的系统审核项。审核范围来自任务及其实际业务动作，不来自已安装工具或接口目录。

本表依据生产 SQLite 的只读任务清单：14 个启用且未删除的 scheduled_tasks，以及它们的命令和 Skill 引用。ID 是当前实例的对应证据，不是运行时代码中的固定许可表。扫描任务可以产生后续业务实例；扫描命令本身与该实例的候选审核分别记录。个人对话中的工具使用不自动成为后台系统审核项目。

只有这些任务实际提交的业务候选才适用对应的 Consumer/Audit/System 契约。纯扫描、下载或登录命令仍走已配置的服务命令及其技术结果验证，不因列在本表而新增 Audit Agent 回合。任务是否需要某个读取能力，仍由该任务的实际事实决定。

本表列出任务职责及审核应对应的业务对象，不表示所有列出的任务都已接入新的审核执行契约。Task3 的生产 dispatcher 调用 WechatReplyConsumer 与 WechatDecisionRunner，持久化候选后由独立发送循环处理 delivery；其中 audit_summary 是既有决策字段，不是独立 Audit 审核回执。本次保留这条既有路径，没有新增微信审核回合，也没有将微信 producer 切换到新 SystemExecutor。

## 每个业务审核项的证据

审核清单和发布验收应能说明：对应哪个实际系统任务、哪一个当前业务实例、什么触发、哪份持久化候选、哪个准确目标或受众，以及哪种结果证据。Audit 审查该候选的业务依据和动作，不把其他任务或个人对话的接口接入当作它的必需条件。

实现已有绑定：AuditTurnContext.task.task_id 与 ReplyTask.id 必须一致；父 Consumer run 必须属于同一任务、执行代和修订，且与完整候选匹配；candidate_digest 与审核 wire 修订必须一致。映射不增加新许可表、路由回退、状态或恢复政策。

| standing_rule_autonomy | 1 消息中的项目请求与已有规则；项目编号不能推定为 OA 身份，缺执行对象时不能宣称签核 |

20 个共享契约样例验证这些任务复用的候选、审核、选择、执行、回执和历史投影机制，不代表新建 20 个业务审核任务，也不证明所有生产任务已经业务完成。
