# Meeting 群候选受众说明去重验证

## 问题与验收边界

六条完整、成功的生产 Meeting 原生 trajectory 在本轮 User 输入的每个候选群里重复同一段
受众核验要求。该段正文逐字相同；群 ID、成员名单、讨论片段和读取状态则属于各群自己的事实。
本轮只把这段要求移到非空候选列表前一次，不删减任何群事实，不改群发现、Agent 结果模型、
受众核验或发送规则。无候选时的服务输入保持原样。

验收要求：旧实现下回归测试失败，新实现下通过；规则原文逐字保留且只出现一次；
候选 JSON 除该重复字段外完全相同；固定匿名会议的选群、对齐结论、责任人、人员敏感内容
处理与严格结果校验不退化；发布后核对正式版本、进程、队列、Attention 和 History。

## 本地与匿名对照

两个回归点先因旧实现仍在候选项里重复字段、列表前没有共用规则而失败，改动后通过。
`tests/test_meeting_alignment.py` 与 `tests/test_meeting_alignment_agent.py` 合计
229 项通过。固定匿名输入以同一份冻结会议 Skill、同一模型和每场 16 个虚构候选群
比较重复规则与共享规则；除规则位置外，候选事实逐项相同，两类会议各重复两次。

8 个原生只读结果全部符合 Pydantic 结构，工具调用为零。精简输入的 4/4 次均满足
预期群、业务结论、责任人和敏感内容检查；旧输入 3/4 次满足全部检查，另一次在
责任人 @ 检查上失败，但选群和敏感内容检查仍通过。每份虚构 prompt 减少
8,480 字符。案例不含真实会议、Work Profile、业务 MCP 或外部发送。

`evals/trajectory_optimization/meeting_candidate_instruction_native.py`、
`evals/trajectory_optimization/meeting_candidate_instruction.native.v1.json`。
