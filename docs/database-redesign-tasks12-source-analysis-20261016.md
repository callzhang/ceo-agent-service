# Twelve remaining Tasks families: native source analysis, 2026-10-16

This is source research for the twelve residual Tasks-directed families, not target DDL or an implemented migration. The approved ten core tables plus Email ledger remain incomplete. The State candidate remains local; this research made no production change.

The current production source contains exactly **134 columns across these twelve families**, all covered by the approved 1,611-field CSV. There are **24 indices including 11 autoindices, 10 triggers, four outbound FK groups, and three incoming FK groups from one retained family**. The only CSV type drift is `workbench_artifacts.turn_id` and `workbench_attachments.task_id`: both are now physical `INTEGER` references to `tasks(id)`, while the original CSV says `TEXT`. Their public IDs remain Workbench UUID strings through projections. No missing source field was invented or silently dropped.

The metadata receipt is [2026-10-16-tasks12-native-source.json](superpowers/specs/2026-10-16-tasks12-native-source.json). Its `tables` member freezes every table/index/trigger CREATE statement, full `table_xinfo`, `index_list`/`index_xinfo` including native implicit ROWID terms, outbound/inbound FKs, external SQL references, and every approved CSV row. Those are the authoritative exact defaults, affinity, nullability, PK ordinal, uniqueness and constraints; the summaries below do not replace them.

## Native identities, constraints and approved destination

All twelve are ordinary ROWID tables. Five have `INTEGER PRIMARY KEY AUTOINCREMENT`: decisions, rounds, OA events, OKR items and WeChat import jobs. Their five allocator streams are independent in the source; `lastrowid` is returned by their writers. No production `sqlite_sequence` value was read. A future shared physical table must preserve public identities and source allocator behavior explicitly; shared target allocation alone does not prove this.

The remaining TEXT/composite PK families have native hidden ROWIDs. Several TEXT PK declarations have `notnull=0`; ordinary SQLite TEXT PK semantics can admit NULL even when application writers require nonblank values. Do not infer native NOT NULL from Python validation. The historical-candidate four-part PK is explicitly NOT NULL. Indices' implicit ROWID ordering, signed ROWIDs, `INSERT OR IGNORE` and `INSERT OR REPLACE` behavior are part of source characterization. Current diagnostics explicitly use classification-task ROWID; historical migration v29→v30 uses historical-candidate ROWID. This research does not claim those hidden IDs must become public target IDs.

## Coupled foreign keys and retained-family SQL

The four outbound FK groups are business mapping→Tasks reply parent, attachment→Tasks Workbench task, artifact→Tasks Workbench turn, and feedback decision→feedback batch. All have native NO ACTION update/delete behavior. There are no cascading deletes.

Exactly three external incoming FK groups come from `feedback_iteration_decision_items`:

| Retained child column | Source parent endpoint | Existing additional fact |
|---|---|---|
| decision_id | feedback_iteration_decisions.id | Required integer; child PK is `(decision_id,feedback_key)` |
| feedback_key | feedback_processing_items.feedback_key | Required TEXT; preserves exact decision membership |
| round_id | feedback_processing_rounds.id | Required integer; references the historical round, not whichever round is now current |

The child table's complete metadata, plus `feedback_processing_transitions` and `feedback_events`, is frozen under `retained_coupled_schema_metadata`. Only decision-items has native FKs. Transitions uses round_id/batch_id/feedback_key in SQL without FKs; feedback_events keys and resolved_at are synchronized by the same transactions. Absence of FK is not absence of coupling. None of those retained families is silently added to this twelve-family migration scope.

The external CREATE-SQL scan finds only those table FK references (plus the decisions→batches internal reference). No external view or trigger references a twelve-family name. The ten own triggers remain captured, including their references into the existing shared Tasks table. A future source preflight must check the then-current source again; this finite result is not an exemption for new references.

Source joins also link feedback workbench_task_id/workbench_turn_id to public Workbench identities and attempt_id/agent_run_id to existing execution/runtime lineage. The declared feedback child FKs cannot be replaced by a single parent pointer: decision, item and round remain independently identifiable, as the approved design explicitly states for the eventual Actions decision-item type.

## Current writers, transactions and lifecycle dependencies

### Current business-object map and reply Tasks

`AutoReplyStore._ensure_business_reply_task` (`app/store.py:9094`) is invoked from reply enqueue/ensure, scheduled dispatch and grouped ensure paths using their caller transaction. It first finds an immutable input by channel/conversation/trigger, then reads the current map. OA provisional-key promotion atomically rewrites the existing reply Task and its inputs, deletes the provisional mapping and inserts the definitive key. A missing map creates a new physical reply Task and map; an existing map reuses its current parent. `replace_pending_single_chat_reply_task_trigger` (`18423`) can repoint mappings. `get_reply_task_for_business_object` (`14203`) joins to the current reply projection.

Mapping ownership affects `reconcile_valid_needs_human_projections`, superseded-failed-task skipping, unresolved-problem attempt lists/counts, operation logs, queue/Attention readers, quality gate, reply deferral and rule-question retirement. These exact owners/lines are enumerated in the JSON. Removing the map while simply making every historical business_object_key unique would change revision behavior. Map timestamps and atomic repoint semantics are source facts needing an exact final mapping, not justification for another long-lived mapping table.

### Email classifier and historical queue

`EmailClassificationTaskAdapter` (`app/email_task_adapter.py`) owns ensure/open/close/purge/get/retry/claim/expire/finish, with exact owner ranges in the receipt. Ensure serializes under BEGIN IMMEDIATE, returns the stable existing task, and rejects a changed immutable input; compacted inputs compare an identity digest that excludes scheduled_consumer. `open_offline_task` uses INSERT OR REPLACE for a caller-ID running row with input `{}`, six-hour lease, generation/attempt 1; close/purge deletes only matching `{}` tasks. This is current native lifecycle, not an abandoned table.

Claim (`444`) performs an empty-read fast path, then recomputes expiration and eligibility under BEGIN IMMEDIATE. It orders pending tasks by created_at/task_id, increments generation and attempt_count, sets running owner/lease and checks one row. Expiry requeues running rows, clears owner/lease and sets available_at/error. Finish (`554`) uses exact task_id + running status + owner + generation CAS; completion selects and compacts input in the same immediate transaction. Failure/defer retains the input. Explicit retry only requeues selected failed tasks and resets the attempt count/result/error/lease without changing generation/identity. No new recovery or authorization behavior is proposed here.

Completion compaction (`compact_done_input_json`, `614`) preserves stable identity, provider locator, input SHA/bytes, configuration and unsubscribe coordinates, plus bounded scheduled-consumer references. `app/storage_maintenance.py:16` is an explicit historical batch, never initialization. Stable UID inventory reads `input_json.provider_locator`, so compacted input fields remain query dependencies. `app/store.py:10344` validates runtime parents for email classification by the public string task_id and running status; that workload key cannot be cast into a shared integer ID. Email durable-row validation (`app/email_store.py:7278`), processing-progress reporting (`15047`), quality gate and Attention query JSON/ROWID/status directly and need caller conversion with the queue.

Historical enqueue (`app/email_store.py:9050`) inserts/upserts candidates and the selected State `email_historical_traversals` watermark in one BEGIN IMMEDIATE transaction. A conflict refreshes digest/locator/UID/timestamp but deliberately does not reset state/reason/retry fields. Listing (`9117`) reserves up to two ready deferred candidates, fills with pending by UID/stable identity, then remaining deferred by attempted-or-updated time. State update (`9164`) requires exactly one compound-key row and applies the existing deferred retry interval. There is no owner/generation claim CAS on this queue. `app/email_worker.py:3723` onward re-reads provider messages using the stored locator and marks pending/deferred/terminal through these methods; this research did not call that provider path.

`_historical_candidate_projection` (`app/email_store.py:1715`) validates account/folder/stable identity and retains only locator coordinates. The v29→v30 migration (`4584`) converted earlier stored normalized_text into its digest and redacted provider JSON. Consequently the CSV's historic body wording is not authority to hash the current digest again, treat locator JSON as a body, or delete either needed re-read coordinate. No production row audit was performed to assert every row's current value conforms.

### Feedback batch, item, round and append-only decision

`claim_feedback_processing_items` (`app/store.py:20354`) uses one immediate transaction to validate the enabled setting, exact requested key count/membership, pending source events and item projections, prior resolved/reopened round history, and zero current-round sentinel. A same-batch retry verifies existing lineage and returns its claims. A new claim creates a processing round with max(round_number)+1 and receipt_version 2, CAS-updates each item from pending/current_round_id=0, appends a pending→processing transition, then advances the batch. Source public round ID and per-feedback round_number are different identities.

`associate_feedback_processing_turn` (`20787`) and `patch_feedback_processing_item_evidence` (`20895`) read exact item/current-round/batch processing membership, update both row forms and check both rowcounts. Evidence patch cannot change processing status. `record_feedback_iteration_decision` (`20122`) requires the exact processing batch, current round membership and one matching Workbench task/turn association; it inserts the append-only decision and all three-endpoint child rows in the same transaction. Grouped reads return decision membership plus round IDs.

`resolve_feedback_processing_batch` (`21819`) checks current lineage, exact item/round/source membership, typed resolution evidence and the existing decision/receipt scope. It writes resolved round evidence, item projections, transitions, source-event resolved_at, and batch resolution with one timestamp and rowcount checks in the immediate transaction. Idempotent resolved readback revalidates the stored receipt. `reopen_feedback_processing_item` (`20559`) requires a valid resolved latest round/batch/source, stamps reopen fields once, appends resolved→pending transition, clears current item association/evidence to source sentinels, and reopens the source event. Old round receipts survive. `_validate_current_feedback_processing_batch_lineage` (`21202`), resolved-round/batch validators, transition multiset/ownership validators and `_resolution_feedback_iteration_decision` (`21671`) must be traced with the SQL conversions, not left reading retired names.

Current item hydration (`19984`) handles some old evidence/attempt values differently from strict round hydration (`20009`). The source initializer also has backfill/guard declaration checks around `1911–2451` and `3772–3830`. Those are historical/source bootstraps; a new selected final release cannot keep materializing retired native families through them. This research does not introduce another validator or modify existing evidence policy.

### OA, OKR and WeChat import

OA event insert/adopt/list/claim/finish methods are `app/store.py:9266–9419`. Insert OR IGNORE uses the channel/conversation/trigger natural key and chooses ignored versus pending by requires_reply. Adoption narrows to the exact process/node, pending/adopted states and required reply. Claim CAS sets sending only from pending/adopted with claimed_attempt_id=0; sent requires the same claimed attempt, while failure returns to adopted and clears the claim. `app/worker.py:2717` delivers only after the existing OA execution result, reconstructing `DingTalkMessage` from trigger_message_json before marking sent/failed. This source payload cannot be retired merely because the row is not pending. No generic TTL or terminal-input policy was added.

`record_okr_review_item` (`17728`) is a plain insert returning lastrowid. `app/okr_review.py:748` writes each normalized adopted review item after the run and before marking its request done. No current literal table reader beyond the insert/bootstrap was found, but that does not establish that the adopted item result is disposable or exactly recoverable from native input. Parent request identity is public numeric ID and the native table does not enforce a request FK. The approved CSV source-retirement label needs an exact source/readback decision before removing item_json; this metadata-only research supplies no such proof.

WeChat begin/finish (`27984/28001`) use `_agent_run_write_transaction(None)`. Begin validates nonblank import/account identifiers and returns a new job ID; no uniqueness deduplicates equal import_run_id. Finish accepts only completed/failed, updates only a running row, returns on the same terminal status+error, and rejects a conflicting terminal rewrite. `app/wechat/memory_import.py` uses it for both import paths. `_runtime_operation_parent_exists` (`10344`) resolves `wechat_memory_import_job:<public id>` and requires running; runtime Attempts still need this parent query after physical consolidation.

### Workbench file metadata and executor lease

`WORKBENCH_ATTACHMENT_SQL` and `WORKBENCH_ARTIFACT_SQL` (`app/workbench/store.py:88`) join physical parents to `tasks.legacy_key`, returning original UUID task/turn IDs. `save_attachment` (`339`) canonicalizes UUIDs, checks task existence, serializes with the attachment file lock, compares idempotent request metadata/hash, writes a temp file, then under BEGIN IMMEDIATE inserts metadata with `task_physical_id`, replaces/fsyncs the file and commits metadata. These operations and the existing cleanup sequence are one source behavior; SQL-only insertion cannot stand in for end-to-end attachment acceptance.

`append_artifact_event` (`881`) checks the running executor lease and next Workbench event sequence under BEGIN IMMEDIATE, inserts the artifact with a physical turn parent, and appends its `runs.workbench_events` row in the same transaction. Timeline/get/list/stats project UUID parents; attachment paths are later delivered to the executor. `list_artifacts` itself queries `WORKBENCH_ARTIFACT_SQL` and therefore has no literal native family reference in its method body; the 94-owner lexical inventory is a starting index, not an exhaustive indirect-call graph.

Startup `_reconcile_attachments` (`2286`) reads metadata and validates the existing UUID directory/path/file relationship before deleting its invalid metadata/files under its existing rules. A conversion must replace its direct deletes and projected reads with the same semantics. No attachment bytes or filesystem state were inspected here, and this source behavior was not executed.

## Existing Tasks release boundaries that constrain the next chunk

`app/task_storage.py` currently has six original Task kinds and explicitly adds the two Workbench kinds through `WORKBENCH_TASK_TABLE_DDL`, with public numeric IDs in per-source legacy_key namespaces and Workbench UUID public IDs in legacy_key. Global physical IDs already appear in Actions, Runs, the three scoped child FKs and other retained children. The current table is wide, despite the final approved explicit typed-payload representation. Its existing `work_summary_inputs.payload_json` is itself a source field; it cannot be confused with a future structural payload envelope.

`create_task_schema`, `_declared_task_objects` and `task_schema_is_current` keep `include_workbench=False` defaults for historical six-kind source releases (`app/task_storage.py:659–718`). Task4B capture/migrate/restore helpers (`734`, `905`, `1034`) and Workbench's separate capture/migrate/inverse declarations preserve different source profiles. `app/workbench_storage.py:263–325` still correctly freezes the pre-conversion Workbench TEXT UUID parent DDL. It must not be edited to imitate current production physical INTEGER parents. Candidate `app/email_current_schema.py` also remains a source factory for the two retained Email queues. A next target release needs a separately explicit selector/profile; changing these historical defaults is not a valid way to activate it.

No target name, payload field, public alias column or trigger policy is specified by this report. The 134 exact CSV rows are migration directions and source meaning, not an executable final twenty-kind Tasks declaration. Existing eight-kind physical identities must not be silently regenerated when the twelve residual families are added.

## Recommended next bounded execution chunk

First turn this frozen capture into a **source-only twelve-family oracle** over the actual metadata and a genuine current fresh source profile, with synthetic in-memory writes. Its useful checks are source defaults/storage classes, native PK NULL/ROWID cases, exact UNIQUE/CHECK/trigger/FK behavior, five independent allocators including ignored inserts/exhaustion, classifier owner/generation CAS, historical traversal transaction/conflict behavior, feedback three-endpoint child closure and current-round transactions, OA attempt CAS, WeChat terminal idempotence, and Workbench public/physical parent projection. The current declaration-roundtrip check alone does not cover those behaviors.

Then prepare the finite field/constraint/caller plan for the final Tasks representation **including the eight already-published kinds as preserved inputs**, using the approved field list and exact current source types. A subsequent implementation can be sliced by independent caller groups, but release/retirement must close the retained feedback decision-items FKs, transitions/source-event SQL, runtime-parent checks, Email startup validation, Workbench filesystem/recovery paths, and current-map diagnostics. Email's two queue families (27 fields, no native incoming/outgoing FKs) are the least FK-coupled residual caller group; feedback's four parents (51 fields plus the retained decision-items endpoints and transition/event SQL) are a coherent later transaction group, not four independent migrations.

This recommendation is grounded in source coupling and introduces no authorization, audit, safety, retention or reconciliation policy. No application/tests were edited, no migration or commit was made, and no provider/native CLI/main/push/deploy action occurred.
