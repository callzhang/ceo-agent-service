# History 可处理状态

History 对审批、回复、会议和任务使用同一套管理者关注状态展示。业务判断仍由各 Agent 和持久化执行结果负责，页面不根据消息正文猜测原因或操作。

## 需要管理者处理

卡片和详情页固定显示：

- 原因：读取已持久化的审核摘要、执行错误或任务结果。
- 外部副作用：读取 Agent run 的 `side_effect_state`；`unknown` 不允许重放。
- 选项：Agent 提供的业务选项，以及当前状态允许的重试、暂不处理、人工处理和技术详情。

在 History 选择业务选项或“暂不处理”时，Web 请求只记录明确指令并重新排队同一个 `reply_task`。原 attempt 的选择状态与任务重排队在同一数据库事务内完成；重复提交同一选项复用同一个 attempt 和执行代次。

审批类“暂不处理”会把以下要求交给 Agent 执行：通知实际申请人审批仍待处理、缺少的材料或事实，以及申请人下一步需要做什么。Web 页面本身不直接发送通知或执行审批。

## 自动恢复

只有同时满足以下条件时才显示自动恢复：

- 持久化副作用状态为 `none`；
- 原 reply task 或 meeting job 仍为可重试状态；
- 持久化记录中存在下一次执行时间。

页面直接读取 `available_at`，显示当前尝试次数、最大次数和下一次自动重试时间，不在渲染时重新计算。回复任务当前最多尝试 3 次。自动恢复卡片只提供技术详情，不提供人工重放按钮；重试耗尽后才转为“需要你处理”。

## 审批状态归并

History 以 OA `process_instance_id` 作为审批事项身份，不以单次 Attempt 作为审批最终状态。`task_id` 只表示流程中的一个审批节点，不参与拆分审批事项。

- Agent 重试、恢复核对和启动前失败都必须从原始 `reply_task.oa_url` 继承 OA 流程与任务标识。
- 同一审批事项只在 History 首页展示一条当前记录，固定选择 `(created_at DESC, id DESC)` 的最新 Attempt；筛选、计数、分页、卡片编号、详情链接、当前系统状态、注意力和恢复入口都以这条记录为准。旧记录保留在审批详情时间线中。
- 业务结果与当前系统状态分开显示。业务结果批量读取当前页所有审批流程的全部 Attempts，并按 Attempt 从新到旧查找持久化强证据；已确认的同意、拒绝或实际退回优先于留言，只有没有终态动作时才保留最新已确认留言。
- 同一 Attempt 的 structured Audit 与 direct receipt 必须全部收集后求唯一结果；相互冲突立即显示“结果未知”，不得回退到更旧证据。没有业务证据时才使用最新 Attempt 的 workflow、`no_action` 或 unknown。
- structured 审批动作只信任 `payload.argv` 解析出的 DWS canonical command、流程标识和需要时的任务标识，不读取模型生成的 operation、capability 或 target 标签。退回还必须是允许的 `revert-task --action`；普通成功回执不能把“退回”猜成已退回。
- 这些归并规则只使用现有持久化字段和批量只读查询，不新增审批 case 表或数据库迁移。

## 安全边界

- `side_effect_state=confirmed`：不显示默认重试或暂不处理，只保留 Agent 已给出的后续选择和只读入口。
- `side_effect_state=unknown`：不显示重试或暂不处理，只允许人工处理和技术详情；任务继续走外部动作核对。
- 会议和任务子系统没有安全重跑入口时，History 不生成新的重跑接口，只链接人工处理和技术详情。
- 终态记录和正在核对外部结果的记录不显示管理者操作按钮。
