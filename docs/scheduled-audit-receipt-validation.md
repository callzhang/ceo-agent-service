# Scheduled Consumer-to-Audit document return

The shared scheduled Agent path can publish a report document in Consumer and then send a message after Audit. In read-only reviews of tasks 405064 and 405301, Audit sometimes relied on Consumer's statement that the document had been written or read back; task 405379 showed an independent Audit document read. This establishes inconsistent evidence handoff, not that those reports were incorrect. A Weekly Report run that failed before Audit cannot be repaired by this change.

The orchestrator now projects only completed `agent_cli.consumer_document_write` returns from the exact current Consumer parent run into scheduled Audit context. It accepts the structured return or the same JSON object in one native text result block or string, as used by Claude; malformed or mixed content is ignored. Audit sees the tool call ID, Consumer run ID, returned operation and document identity, and a SHA-256 digest and byte count of the returned readback object. No report body is copied. A scheduled Audit with no matching return sees an explicit empty list; other task channels do not receive this section. The projection says what the tool returned and does not claim that report facts or document contents were independently verified.

The first isolated candidate interpreted `provider_result.verified`, `readback.success`, and `readback.markdown` as universal fields. The actual daily report writer fixture returns `provider_result.nodeId` and `readback.content`, so that interpretation falsely reported failure and an unknown content match. The regression test failed on that candidate and passed after replacing those derived booleans with the exact returned readback digest. Tests also exclude failed or foreign-server calls and cover task/generation/role binding plus end-to-end scheduled Consumer-parent-to-Audit wiring.

The affected orchestration, context, and scheduled-consumer files pass their focused suite. This is local deterministic evidence: it does not demonstrate a new native model Audit decision or a production scheduled run. No historical report is replayed, and no external message or document is sent by these tests.

An isolated native Codex check used a local, fictional `agent_cli.consumer_document_write` MCP server that only returned a synthetic object. The completed native event hydrated as `item.completed` / `mcp_tool_call` with a `content` result; `_scheduled_consumer_work_receipts` extracted one receipt from it. No business MCP or real document was touched. Older completed scheduled sessions were no longer available in the local native session inventory, so their saved run records could not verify this read path retrospectively.

The fixed [anonymous read-only comparison](../evals/trajectory_optimization/scheduled_audit_receipt_native.py) uses the actual `AuditTurnContext.render()` with the same fictional candidate and only the service receipt section varied. Across three runs per arm, the [saved results](../evals/trajectory_optimization/scheduled_audit_receipt_native.v1.json) identified no returned readback in the empty case (3/3) and the exact synthetic tool-call ID in the returned case (3/3). Both arms treated report-content verification as absent (6/6); all six runs exited successfully with no tool calls. This is a bounded interpretation diagnostic, not the complete `AuditAgentResult` contract or a production scheduled Audit decision.
