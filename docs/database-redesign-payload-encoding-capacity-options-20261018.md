# Actions/Tasks payload encoding: bounded capacity options (2026-10-18)

## Decision boundary

**No capacity solution or runtime change is selected.** A fixed-order, per-`record_type` JSON value vector is a credible way to remove repeated outer field names while retaining one row per fact, the same scalar codec, source fields, public identities, physical references, generated query columns, and indexes. The smallest contained trial is `reply_attempts`; a whole Actions/Tasks conversion has a larger ceiling but still cannot be called a solution to the observed active-byte regression without a same-input copied-data test. Neither option deletes business data, source rows, indexes, or a second copy hidden elsewhere.

The approved design calls for an **explicit, version-managed typed payload schema** with source field meaning, types, CHECK/unique/FK behavior and queryable constrained projections (`docs/superpowers/specs/2026-10-11-database-redesign-design.md:37-43`). It names `payload.<old field>` as a *field disposition*, and says the final SQL paths must be specified; it does not require a JSON object wire shape. A fixed array of scalar slots is therefore a possible *new reviewed representation choice*, not an authorized silent codec swap. The design's ban on putting multiple historical attempts into one array (`:68`) remains intact: each attempt is still its own `actions` row. The current DDL explicitly requires outer JSON objects, so an array cannot be written under the present schema (`app/action_storage.py:435`, `app/task20_definitions.py:668`).

## Finite options

1. **Contained `reply_attempts` vector.** Use its current source-variant field order, 57 slots in the measured actual variant, with `record_type` and the schema version defining each position (`app/action_storage.py:142-152`, `:454-461`). Keep `legacy_key`, one row per attempt, current physical relations, original defaults, and the `_reply_payload` scalar encoding. Convert its generated `attempt_*` fields, CHECKs, insert/update paths and migration/inverse to `'$[n]'`, with `json_valid`, array type, exact length, per-slot encoded-value checks, and existing required/type/enum rules. The currently global object CHECK would need a finite `record_type` branch; this is intentional schema selection, not a read fallback. Its **17,066,128-byte** serialized ceiling is the highest single-kind saving and tests the mechanism with one Action writer/projection owner. It cannot close the total measured gap alone.
2. **All finite Actions and Tasks vectors.** Assign one immutable field-order tuple per kind/source variant from the existing field maps; keep the identical encoded scalar for each slot. Replace every outer object path and `json_remove(...)= '{}'` shape check with an indexed path, exact array length and existing value/type/business checks. Preserve all generated column names, affinities, FK endpoints, indexes and source-shaped/public/inverse projections. The measured serialized ceiling is **38,635,005 bytes**, about 19.8% of the two current outer payloads. This reaches more kinds but has broad writer and SQL-path cost; even an exact byte-level conversion is insufficient by itself to establish a smaller active database than the source.

The smallest useful **experimental** choice is option 1. If the program requires one capacity-oriented implementation, option 2 is the only option here with a material cross-table ceiling; its adoption requires a separate explicit representation decision and copied-data evidence. No option is selected as satisfying the ten-core-plus-ledger capacity objective.

## Exact preservation and source touch points

For either option, `record_type` and schema version determine a fixed position; no per-row field map, extra table, sidecar object, or permissive unknown-field decode is added. An accepted row has exactly the declared arity and each slot passes the existing encoded-value predicate. Required versus nullable positions retain SQL `NULL` behavior. Native integer `0` and REAL `0.0` remain distinct through `_encoded_native_sqlite_value`; BLOB hex, finite REAL significand/exponent, and nonfinite tags remain unchanged (`app/action_storage.py:1000-1050`; SQL decode/check `app/action_email_definitions.py:606-635`). Nested source JSON remains **TEXT in one slot**, not a parsed or deduplicated body. Source defaults still execute at the original SQL write point (`app/task8_storage.py:76-109`, `app/task12_storage.py:184-221`). Current missing-key acceptance should not be inferred from a `null` slot: measured rows are fully populated; future unsupported shapes must fail until a new versioned declaration explicitly maps them.

Known directly affected code for option 1 is `app/action_storage.py` (reply field order, global outer CHECK, generated reply fields, `_reply_payload`, insert/update, migration and inverse). Option 2 additionally reaches Action declaration/projection builders in `app/action_email_definitions.py`, `app/action_followup_sync_definitions.py`, `app/action_task_delivery_definitions.py`, `app/action_error_definitions.py`, `app/action_feedback_definitions.py`, `app/action_business_definitions.py`, `app/action_email_history_definitions.py`, and `app/action_skill_config_definitions.py`; Action writer/copy owners in `app/action_email_storage.py`, `app/action_followup_sync_storage.py`, `app/action_task_delivery_storage.py`, `app/action_error_storage.py`, `app/action_feedback_storage.py`, `app/action_business_storage.py`, `app/action_email_history_storage.py`, `app/action_receipt_storage.py`, and `app/action_storage.py`; and Task definitions/writers/copy/inverse in `app/task20_definitions.py`, `app/task8_storage.py`, `app/task12_storage.py`, and `app/task20_schema_release.py`. `app/state_storage.py:150-156` currently supplies Tasks' keyed `json_set` SQL and needs either a Task-specific positional equivalent or an explicit parameterized extension without changing State. Literal outer paths also occur in `app/action_business_storage.py:502-532` and `app/action_storage.py:1112-1222`; shared generated fields whose ordinal differs by kind need a `record_type`-specific CASE, not one global index. `app/workbench/native_events.py:201` and `app/audit_web.py:3378-3383` address **nested Runs/source JSON**, so their literal paths are not an instruction to vectorize that content. This is a finite source-derived touch inventory, not an applied patch.

## Checks required before an implementation can be accepted

In a bounded SQLite `:memory:` diagnostic only, five real `reply_tasks` field names were assigned synthetic `NULL`, integer `0`, REAL `0.0`, BLOB `00ff`, and nested-JSON-as-TEXT values using the existing codec and indexed SQL decoder. SQLite 3.53.4 returned the expected storage classes and values; an indexed generated-column point query used the synthetic index. Short/long arrays, an outer object and an unsupported nested object were rejected by exact arity/type checks. This proves only that SQLite can express the required basic array mechanics. The in-memory connection was closed; no temporary file or copied/source DB was created.

Before a scoped code change: pin the exact source/runtime snapshot; enumerate every direct outer `payload_json` SQL path and every source-variant field order; run focused RED/GREEN tests for defaults, nullable/absent distinction, `0`/`0.0`/numeric-looking TEXT, BLOB, nonfinite REAL, nested JSON text, malformed arity/tag, unknown record type, FK/CHECK/unique failure, writer SQL expressions and CAS, original public reads and inverse. Verify generated-column point reads and actual query plans, including parent FK indexes, against the original declarations. Finally run the existing authorized **same-input disposable copy** protocol on both unchanged and candidate builds: exact forward and inverse source values/storage classes, IDs/ROWIDs/waters, all business fields, active and allocated pages, `dbstat` per-object allocation/unused bytes, and representative claim/lookup/History performance. A smaller serialized payload is a diagnostic; only that copied-data gate can establish capacity behavior. No live source, provider, native CLI, constructor, repository tests, or deploy was used here.
