# Frozen Skill repeated-read acceptance, 2026-10-18

## Problem and evidence

The complete paginated native history records repeated `read_task_skill` calls in Consumer sessions that process successive messages for one conversation. In 106 recent service sessions, 90 calls across 16 sessions returned an identical Skill result already read earlier in the same session; 78 of those had no intervening context-compaction item. These are read costs, not failed business outcomes. The count is a screening inventory; eligibility still requires identical selected frozen source identity and a retained complete prior read.

For example, session `01a14c52-f271-7c60-ba62-dfd5369996ae` has two completed turns. Both Task inputs advertise the same two frozen-content SHA-256 values. Each turn reads `ceo-message-triage` and `dingtalk-chat`; each second result is byte-identical to its first result, with no compaction item between them. Both turns then read current DingTalk context and produce valid no-action judgments. A second two-turn session, `01a148fe-49d9-7801-bd1d-abd387c134f3`, shows the same pattern. The prompt exposes the SHA values but no longer says the already loaded, unchanged content may be reused. Commit `3f00ea6d1` removed that condition while compacting discovery text, after PR #62 had implemented and validated it.

## Finite acceptance

The candidate should avoid rereading exact frozen Skill content on a same-session continuation when the prior complete content remains available and the selected source SHA is unchanged. It must read on a fresh session and when the selected source changes; it may reread after compaction or when the prior content is unavailable. It must continue to read current source facts on each turn. Audit independently loads its selected frozen Skills. The outcome, target, cross-time-zone conversion, deduplication and typed result for the existing anonymous fixed cases must not regress.

Change only the frozen Skill discovery instruction if the fixed comparison supports it. Run the focused discovery tests, then a matched anonymous read-only cold/continuation/changed-source case using the same route, model, facts and complete frozen Skill bodies. Compare actual native read calls and material judgment, not just valid JSON. Existing PR #62 evidence supports the old wording, but the later discovery change requires a fresh comparison before this change can be accepted. A failed comparison is a no-go; no extra retry, cache, or task-specific rule is added.

After review and merge, use the repository deploy path. Read back the production commit/PID, health, queues, Attention, History and current Settings Task preview. This operational readback does not by itself prove that a natural future Consumer turn will skip the repeat read.

## Fixed comparison and decision

A one-sentence candidate was first covered by a regression that failed on the current code and then passed with the candidate; the three focused test files passed, 46 tests total. One native fixture attempt was invalid because it disallowed all MCP approval, and a second could not resume because its CLI flags were in the wrong position. Neither is business evidence. The corrected fixture kept the synthetic facts, two complete synthetic Skill bodies, Codex OAuth route and tool set fixed between arms, and changed only the discovery sentence. Each arm used its own fresh session for cold, same-session continuation, then one changed frozen body. All six completed native turns used only read-only fixture tools and produced the expected no-action, no-action, reply judgments. Tool calls were identical: cold read both Skills and current context; unchanged continuation read current context only; changed-source continuation reread the changed Skill and current context. See the sanitized counts in `evals/trajectory_optimization/frozen_skill_reread_no_go.v1.json`.

The candidate produced **zero fewer reads** in the matched case, so the acceptance condition failed. The code and test edits were withdrawn. The production repeats remain real, but this fixture does not reproduce them; the old discovery sentence alone is not a confirmed cause. The long production Skill text and task-specific instruction ownership are possible differences to examine in a separate, bounded diagnosis. Do not ship a speculative reuse prompt or claim a general token improvement from this comparison. This is a documentation-only no-go, with no runtime deployment.
