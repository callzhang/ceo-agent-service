Scope: source inspection at `580ebf6b5` on 2026-10-19, with aggregate-only `mode=ro` reads of the production SQLite database. This is an implementation map, not a data conversion or approval to retire historical facts. Numeric public IDs are scoped to their existing `record_type`; the physical `tasks`, `runs`, `business`, and `actions` containers do not make their records semantically interchangeable. Current schema/projection definitions, rather than retired physical-table names in historical migrations, define the fields below.

## Smallest implementable slice and later decisions

1. **Smallest safe unit: finish caller ownership, no row retirement yet.** The key separation already exists: `retrieve_task_semantic_context` reads semantic Tasks/projects only and `task_agent.apply_task_agent_decision` writes semantic records. `retrieve_project_candidates`, `retrieve_project_task_details`, `load_project_task_detail`, and the `/tasks/legacy-project`/`task_management_*_payload` paths still read WorkProjects/Todos/Updates. The next implementable code slice is to make those legacy search/detail payloads explicitly historical wherever they are presented, and keep only the semantic context in the current Task Agent decision path. Do not remove the legacy payload or provider methods while Console/legacy task-management callers still use them. No business or run field can be deleted solely from today's counts. This avoids inventing mappings for 3,327 unmapped Todos and 975 unregistered Projects.
2. **Candidate schema reduction after a verified inventory:** the `business_object_tasks` mapping could become a typed alias-edge projection only if it preserves multiple keys per reply task, key uniqueness, OA alias selection, timestamps, deferral/History queries, and current mapping behavior. Retire neither the mapping nor its data merely because `reply_tasks.business_object_key` exists. The event/error duplication hypothesis is weaker: only 183/1,157 current-parent errors match; keep `agent_run_state_events` as historical chronology.
3. **Separate product decisions:** decide whether legacy open Todos remain a supported working view or only history; how `waiting_owner`, follow-up question/priority/blocker/completion evidence map to semantic Task and follow-up models; whether 975 legacy WorkProjects are ever merged with official registry Projects or semantic clusters; and whether real DingTalk Todo IDs and completed outbox receipts should be reparented to semantic Task IDs. None follows from equal titles or physical table consolidation. A selected conversion must require source-level evidence and preserve all old IDs/receipts.

For any later destructive migration, freeze a read-only aggregate/source manifest first, including per-type counts, current linkage cardinalities, unresolved outbox statuses, real provider IDs and exact DDL/indices/triggers/sequence. Capture declaration metadata, not a stale row image. Convert inside one FK-off transaction with source-digest checks, preserve public IDs/storage classes and untouched payload bytes, compare both source→target and target→source identities, and publish schema markers atomically. The paired inverse must reconstruct **current** facts (including writes after forward migration), IDs, sequence watermarks, aliases and receipts into the original typed declarations; a database backup is a safety copy, not an inverse. Refuse unsupported populated alternatives rather than silently classifying them. This follows the existing Store release pattern (`app/business_legacy_owner_storage.py`, `app/run_storage.py`, `app/state_schema_release.py`); it is a constraint for a future scoped change, not a proposal to add new audit gates.

Evidence boundary: source read and SQLite aggregate reads only. No provider call, runtime write, import apply, schema conversion, test, deploy, or private body export was performed for this map. Live counts may change while the service runs.

## Authorized target C: one executable Task lifecycle

The existing `tasks` table is only a physical union. `app/task20_definitions.py` places each executable kind's `status`, `attempts` (or `attempt_count`), `available_at`, `error`, and timestamps in `payload_json`, while `app/dispatcher/adapters.py` repeats due/claim/release SQL by kind and `state/dispatcher_claim_leases` owns another claim generation/owner/expiry. Merely adding a common facade over those writers would perpetuate two state owners. The target is one physical lifecycle on `tasks`, with `id`, `record_type`, `legacy_key`, `parent_id`, `current_input_id`, `claimed_input_id`, and typed domain payload retained; physical `status`, `available_at`, `attempts`, `error`, `created_at`, `updated_at`, `lease_owner`, `lease_expires_at`, `owner_pid`, `generation`, and source-qualified active `adapter_name` become the **only active scheduler/claim state** for executable kinds. The latter claim fields are source-backed copies from kind payload or `dispatcher_claim_leases`, not inferred business facts. `locked_at` is the source job-lock timestamp and remains a distinct field; it is neither a lease expiry nor proof of current ownership. Preserve each kind's actual null, empty-string, and default distinction. Source public IDs and natural-key unique indexes remain. Non-executable kinds have NULL generic lifecycle fields and keep only their own domain fields. Old field-name projections may aid a one-release conversion but may not write a second scheduler status.

The remaining eleven Task20 kinds are **not** independent execution jobs: `reply_task_inputs` is an input-version child; `workbench_tasks` is the parent conversation/container; `business_object_tasks` is an alias edge; `email_historical_candidates` is an email selection record with its own `pending/deferred/terminal` domain state; `feedback_iteration_decisions` is append-only decision evidence; `feedback_processing_batches` is aggregate scope; `feedback_processing_rounds` is a round/receipt history; `oa_notification_events` is an inbound/adoption/send journal with provider identifiers; `okr_review_items` is result detail; `workbench_artifacts` and `workbench_attachments` are output/input references. Keep their exact source fields and typed parent constraints. They may later move to Actions/Emails/Runs or remain typed children of `tasks`, but none should receive a fake `pending` generic lifecycle, and their domain `status`/`state` must not be treated as a second scheduler status. In particular, `oa_notification_events` must still link to the reply-task adoption and sent Attempt receipt; cancelling its *standalone* queue interpretation does not cancel the journal.

**One writer, existing dispatcher interface.** `enqueue(kind,natural_key,domain_payload)` inserts one typed row with source identity and the kind's real initial lifecycle state, or returns the existing row under its current uniqueness rule; reply-task new input still appends `reply_task_inputs` and updates current pointer/version in that transaction. `claim(kind,adapter_name,channel_or_due_filter,owner,lease)` selects due work, verifies live-owner protection using the existing owner/PID/expiry facts, and atomically writes the Task's active owner, PID, expiry, generation and source-qualified adapter identity, plus the kind's status/input/attempt transition. For reply, meeting and WorkSummary, successful claim increments source `attempts`; a claim release reverses that increment while retaining the monotone fencing `generation`. For OKR, source attempts remains absent and the envelope attempt is ledger generation. `finish(id,generation,owner,outcome,error,available_at)` fences on the Task active claim and performs the source-kind result/receipt mutation in one transaction; release/retry preserves each kind's original due and error semantics. Keep `ScheduledTaskQueueAdapter`, `ReplyQueueAdapter`, `MeetingQueueAdapter`, `OkrReviewQueueAdapter`, and `WorkSummaryQueueAdapter` as the existing dispatcher protocol surface, but make their `claim/release/metrics` use this one Task lifecycle operation rather than source-specific SQL plus a ledger claim decision. `dispatcher_claim_leases` can remain as a passive, source-qualified metadata/history projection for inverse fidelity: it must never be queried to arbitrate, renew, or fence a migrated active claim, and its only updates are derived in that same Task transition transaction. Unrelated action-outbox leases keep their existing owner until separately scoped. Do not add another adapter or a shadow `task_status` in JSON.

**DDL and inverse:** build the target from finite source declarations in `app/task20_definitions.py` and the actual `state/dispatcher_claim_leases` declaration. Put lifecycle columns on `tasks` once, with typed checks and due/claim indexes for executable record types; leave payload to exact domain fields (including input provenance, meeting decision, feedback evidence and result references). Preserve source public IDs, sequence watermarks, natural keys, parent/input FKs, JSON storage classes/bytes, every active claim and `locked_at` separately. Preserve each retained ledger row's **`adapter_name`, `source_id`, `owner`, `owner_pid`, `generation`, `lease_expires_at`, `terminal_at`, `last_error`, `created_at`, `updated_at` and ledger public identity**. These cannot be reconstructed from a Task's current status or timestamps: two reply adapters can have distinct keyed ledger rows, and a terminal ledger row has its own terminal/error time. Keep the rows as passive metadata/history (or an exactly invertible source-qualified representation), including rows written after cutover by the single Task transition transaction; historical pruned rows need no synthetic reconstruction. Refuse a source row whose active payload and ledger claim conflict rather than choosing a winner. The paired inverse rebuilds source-shaped JSON and the original ledger state from **current Task lifecycle plus retained ledger metadata**, including post-forward claims, releases, retries, inputs, stops and completions. It restores exact declarations, public IDs and allocators, not a stale backup. `app/task20_schema_release.py`, `app/state_schema_release.py` and existing schema-factory predicates are the release integration points. Tests must compare the multi-adapter ledger key, metadata timestamps, terminal/error fields, locked-at distinction and current-fact round trip for each executable kind.
