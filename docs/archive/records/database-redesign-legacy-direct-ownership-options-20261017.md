# Legacy semantic import: direct ownership field disposition

Design investigation only. This note does not select DDL, change a caller, or waive the source/inverse proof. The approved target is **10 core tables plus the migration ledger**, with `business_legacy_links` resolved through verified direct ownership and `legacy_key`, not a generic links table ([design](superpowers/specs/2026-10-11-database-redesign-design.md:73)). The [import-result component plan](superpowers/plans/2026-10-17-legacy-import-result-component-plan.md) is an unselected preservation option; keeping all 12 old columns in Actions is not an approved product requirement. Derek allows retiring demonstrably redundant fields and functions. These claims use the [selected-12 source capsule](database-redesign-legacy-import-source-capsule-20261017.md), current source, and scoped tests; no actual-12 copy or native DML was run here.

## Located writer and observable contract

The only located application DML reader/writer of `business_legacy_links` is `apply_task_semantic_import_manifest`: per item, it validates the manifest/source and supporting digest, looks up a row by the unique legacy-source column, rejects a conflicting result, skips a matching result, or inserts after creating a formal Task / finding an official Project in `business_task_transaction` ([source](../app/task_semantic_import.py:497)). The CLI dispatches that function ([caller](../app/cli.py:5236)). `_link_column` accepts three source kinds, but the planner currently marks every WorkProject and WorkUpdate `history_only`; only source-backed WorkTodos can currently be `formal_task` ([planner](../app/task_semantic_import.py:255)). The official-Project branch is implemented but currently unreachable from a planner-produced WorkProject item because `matched=False` and the registry key is empty ([planner](../app/task_semantic_import.py:274), [branch](../app/task_semantic_import.py:529)). A manually supplied manifest cannot simply activate it: `_check_manifest` compares it to a freshly computed plan ([validation](../app/task_semantic_import.py:390)). History-only creates no mapping. The result exposes five counts, with no link row ID or timestamp ([return](../app/task_semantic_import.py:565)).

The bounded exact-name search of `app/` found the two runtime SQL sites above, schema/guard/migration references, and no application consumer of `business_legacy_links.id` or `.created_at`. The focused import tests assert target lookup, retry, conflict, pre-write refusal and history-only behavior; they do not consume those two fields ([tests](../tests/test_task_semantic_import.py:135)). Other tests insert alternate source/target combinations to prove **old schema and migration** behavior ([business inverse fixture](../tests/test_business_schema_release.py:130), [Action fixture](../tests/test_action_business_storage.py:138)). Those are valid source oracles, not evidence that application code produces every combination. This is a bounded repository finding, not a claim about external SQL clients or future features.

The selected-12 declaration has zero inbound FKs, seven possible target columns, three possible source columns, two exactly-one CHECKs, three source UNIQUE constraints, ten outgoing immediate `NO ACTION` FKs, an `(task_id,id)` index, an AUTOINCREMENT ID, `created_at` default, and WorkUpdate kind/public-ID guards ([literal capsule](database-redesign-legacy-import-source-capsule-20261017.json)). Accepted actual-13 evidence records zero link rows; fresh selected-12 also has zero rows and no sequence row. **Actual-12 production-copy rows, sequence and native outcomes have not been bound.** Zero rows and no inbound FK support retirement analysis; neither proves that old source DDL had only two legal target types.

They are supported old-schema alternatives, but no located application producer selects them. Retire them from the **new importer contract** only after the real source/dependency audit and an explicit choice to stop supporting arbitrary legacy link writes. | Old schema permits them for each of three old sources; test fixtures exercise some. The direct owner reference should follow existing typed-public FK practice: the current link points to `business(task_public_id)` or `business(project_public_id)`; those are generated only on the matching `record_type` and have unique indexes ([Business declarations](../app/business_definitions.py:303), [indexes](../app/business_definitions.py:381)). Business `id` is the new physical key, while `legacy_key` holds the old public key and `public_id` casts it. Existing Business intra-table references additionally pair a physical ID with kind/public fields for type safety ([reference pattern](../app/business_definitions.py:339)). A physical owner target is also possible if it uses that composite convention, but it needs a correctly resolved physical ID and type guard. The typed-public FK is the smaller translation of the **existing** link's public-ID FK. Signal's generated Action public alias follows the same pattern ([Action declaration](../app/action_business_definitions.py:101)). WorkUpdate alone uses physical Actions ID in the old link, so any retained WorkUpdate alternative must resolve public manifest ID to that physical row before lookup/write/inverse.

## Constraint translation and option comparison

**Preferred, conditional: inline owner FK.** For the reachable WorkTodo→Task path, a nullable typed target FK on the existing WorkTodo is enough to represent successful import; the FK's non-NULL value is the existing idempotence marker. Keep the import transaction, source/digest/evidence recheck, `_existing_link_matches` semantics and counts, projecting the owner's target as source-shaped `task_id` for the caller. A single WorkProject→Project FK preserves the latent official branch without seven endpoint columns on every source kind. This is direct ownership, uses no new business fact, and avoids an extra Action row. It also makes the current unique-source rule structural: one owner row has one target slot. Scope each slot to its source record type, and forbid a WorkTodo from claiming an official Project or a WorkProject from claiming a formal Task unless a separately evidenced producer requires it.

The old *child* FK blocked deletion/update of a linked source parent. Reversing the pointer does not reproduce that restriction: a WorkTodo with an outgoing Task FK can still be deleted. If source compatibility is retained, translate the old restriction for a linked WorkTodo/WorkProject via the existing direct-owner mutation path or a narrow source-kind guard, including `legacy_key` changes. Keep normal unlinked source mutation behavior. The old target FK already blocks deleting/changing the referenced target public ID and can remain a typed-public FK. The old WorkUpdate kind and public-ID guards remain necessary only while its alternative or historical links remain. Exact SQLite exception class/code and `INSERT OR IGNORE` behavior require native comparison; this note does not assert parity.

**Fallback if full 7×3 old DML and link identity must remain supported: one finite import-result Action.** A typed Action with mutually exclusive source FKs and target FKs can reproduce every old endpoint, old `id`/`created_at`, UNIQUE source constraints and sequence. It is an actual completed internal import result, not a provider receipt. But that is effectively the 12-field link relation moved into Actions; it requires new generated columns, checks, kind guards, source FK constraints, inverse mapping, and a new Action allocator. It meets the table count while adding more schema than the current writer needs. A compact Action with just two targets has no advantage over inline ownership for a one-owner result. Do **not** introduce an arbitrary `from_table/from_id/to_table/to_id` relation or make the same 12 nullable columns universal to all Actions.

The earlier [source analysis](database-redesign-legacy-import-source-analysis-20261017.md) favored the full-preservation Action as the smallest *preservation* route; this note applies the approved direct-ownership criterion and the now explicit permission to retire no-value fields. The recommendation is therefore inline **if** actual-copy/dependency evidence supports narrowing the old DML contract. If full source-schema behavior is a product requirement, the finite Action is the honest alternative; it should be selected for that reason, not to reach 11 tables.

## Required selection and inverse evidence

Before selecting either design, bind the current actual-12 consistent copy: link rows with every field/value/type, `sqlite_sequence` independently of `max(id)`, all target/source parent rows, complete FK/index/trigger declarations and inbound references. Search current caller/source SQL and external integration ownership for every link endpoint plus link `id`/`created_at`. The current exact-name application search found no runtime consumer beyond import; it cannot rule out external SQL. Record whether production has ever used a legacy-link locator or sequence that must survive. If any row uses an unsupported endpoint, inline-two-FK migration must stop or gain a source-derived direct owner; do not silently discard it. If source rows and sequence are absent and no consumer exists, retire link-local ID/time and unused alternatives explicitly. If a burned sequence exists, choose whether that unobserved allocator state is intentionally retired or must remain reversible.

Then define an old→new→old current-fact inverse that includes public versus physical identity resolution, NULL/value types, source owner, target, and any retained ID/time/sequence facts. Compare native before/after import, idempotent retry, conflicting target, source-digest refusal, history-only, old-parent deletion/public-ID mutation, target deletion/public-ID mutation, WorkUpdate kind/public identity, duplicate source and multi-source-same-target cases. The WorkUpdate pre-history lookup bug requires a source-specific test whether its mapping alternative is retained or retired. Historical source fixtures that insert all seven targets remain old-source oracles; selected-current tests should assert only the newly selected contract. No test, constructor, database probe, runtime edit, provider call, network action, or migration was performed for this note.

The unresolved product decision is narrow: **must newly written semantic imports still support all seven target and three source alternatives, preserving unused link identity/sequence, or may the contract be reduced to the current source-backed WorkTodo→Task path plus the latent WorkProject→Project path?** The approved spec's direct-ownership wording favors the latter; an actual-12 populated/dependency finding could override it.
