Read-only investigation on the isolated `business-model-plans` checkout at `580ebf6b59d85df21133193d42721bee12d89e61`, against the deployed `d6a1b024` lineage. This is an implementation specification, not a schema change. Production metadata was queried through SQLite `mode=ro` on 2026-10-19; no row bodies or private values were exported. Recount immediately before a copy migration because the live email count moved from the earlier plan's 9,483 to 9,487.

## A1: selected branch from the bound candidate

`app/action_storage.py` freezes `SOURCE_ACTION_DDL` and `SOURCE_COLUMNS` for six historical source tables. Current Actions uses `_kind` integer type codes, `legacy_key` for the public ID, a separate physical `id`, physical parent FKs, and positional JSONB arrays. `action_payloads()` builds a `PayloadLayout` whose field path is `$[index]`; `_action_definitions()` emits virtual columns, shape/type checks, indexes and triggers; `_current_objects()` is the exact declaration factory. The selected branch is currently one slot in `PAYLOAD_FIELDS['candidate_selections']`, generated `branch_json`, and `CANDIDATE_SELECTION_SQL`. Do **not** remove it from the frozen historical TEXT source DDL or alter the existing old-schema fixture factories. Introduce an explicit new target model/version in the Actions layout/declaration/projection factory, with only the selection layout omitting this slot. Keep `ACTION_RECORD_TYPES` ordering/codes and every other record layout fixed. Expose both old and target declaration factories for the paired inverse and cold-opener validator (`final_action_schema._declarations`, `email_canonical_storage._action_objects`, `action_email_schema_release`/Store version selection).

The current writer is `ReviewedCandidateStoreMixin.select_candidate_option` (`app/reviewed_candidate_store.py:232-251`): it finds `option_key` in `candidate_json.decision_options`, checks for a bound plan or skipped terminal outcome, rejects a conflicting prior selection, then stores `_json(branch)`. Its candidate is selected by its exact `candidate_id`, not by task or latest generation. A target helper should resolve the same option by this stored ID and key, require exactly one key match, and return that object for runtime, UI and inverse; the persisted candidate digest and review binding remain unchanged. The current selection table has **zero** live rows, but new writes and historical synthetic rows still need the full contract.

The complete app search for `branch_json` finds executable readers in `reviewed_candidate_store.py` (current row, claim, completion, begin action, prior action reconciliation, receipt validation, historical evidence), `system_executor.py` (prior action comparison and selected plan), `worker.py` (OA selected branch), `dingtalk_delivery_repair.py` (historical send repair), and `web_api/attempts.py` (attempt detail). `app/store.py`, `quality_gate.py`, and `audit_web.py` join selections to test *existence* and need the selection ID/option key, not a branch body. `get_verified_action_source()` and `list_human_decision_evidence()` currently select `s.branch_json`; either project the derived branch at the method boundary or pass `candidate_json` and `option_key` to their callers. `web_api/attempts.py` already has a fallback deriving the option from candidate JSON; make it the one path. A repository-wide `rg` after editing must find no target runtime `branch_json` lookup; legacy source/inverse and frozen tests are expected exceptions.

The forward copy transaction must first verify for every existing selection: candidate exists by `candidate_id`; candidate JSON parses; exactly one option has `key == option_key`; `_json(option)` equals the old `branch_json` **byte for byte** (or explicitly account for a historically accepted noncanonical byte representation). Do not choose the latest candidate. Rebuild Actions with the target factory and repack each selection's old positional payload minus `branch_json`; other rows should project/repack through their exact existing layouts, preserving SQLite scalar types and physical/public IDs. Recreate exact owned indexes/triggers and check FK/integrity plus source/target row and identity projections before commit. The inverse reconstructs the old selection payload by inserting `_json(bound_option)` at the old slot, using *current* candidate and selection rows, including selections written after forward migration; it then rebuilds the frozen declaration. If a current candidate no longer resolves the selected key, inverse fails rather than inventing an empty branch.

The target declaration delta generated by `action_payloads`/`_action_definitions` is precise: `candidate_selections`' JSONB array becomes one element shorter, the `branch_json TEXT GENERATED ALWAYS AS (...) VIRTUAL` column disappears, and that record type's shape CHECK expects the shorter array. `candidate_id` and `review_id` remain physical FK columns; `option_key`, `status`, and `created_at` keep their existing slots and SQLite types. The public projection no longer selects a generated branch column. No `_kind` code, public key index, or parent FK is renumbered.

Minimal focused tests: two different decision options and selected plan/stop outcome; same selection replay versus conflicting key; superseded candidate still returns old bound option; missing/duplicate key and differing historical branch refuse forward; new target selection survives inverse with old public/physical IDs and `selection_id` FK; both real Actions source variants (`actual_no_memory_fk`, `fresh_memory_fk`) and compact JSONB declaration comparison. Include `tests/test_reviewed_candidate_store.py`, `tests/test_reviewed_candidates.py`, `tests/test_action_storage.py`, `tests/test_system_executor.py`, `tests/test_dingtalk_delivery_repair.py`, and `tests/test_console_attempt_detail_api.py` at the affected nodes.

## A2: receipt owns a confirmed provider result

`ReviewedCandidateStoreMixin.record_candidate_external_action` (`app/reviewed_candidate_store.py:582-627`) currently writes the same `provider_json` into `external_action_results.provider_result_json` and a verified attempt's `result_json` in one transaction. It computes `result_digest` from the canonicalized receipt bytes and has an existing ambiguous-to-sent correction path; preserve that path and receipt identity. `record_prior_candidate_action_reconciliation` also writes a receipt and a verified prior attempt. `record_candidate_action_outcome(status='verified')` permits an attempt-specific value after checking that a receipt exists; do not assume every verified attempt value equals the receipt.

Use SQL NULL in the **new target** attempt result slot to mean: this verified attempt's provider result is obtained through its existing `external_action_key`. Source attempt `result_json` is NOT NULL and defaults to `'{}'`; the target JSONB layout keeps the field but adds it to `NULLABLE_PAYLOAD_FIELDS['candidate_action_attempts']`, changing its CHECK to accept JSON null. Its public projection can return `None`. On forward conversion set `result_json=NULL` **only when** `status='verified'`, the receipt exists, and the two raw strings are equal; preserve every unequal string, including the production `{}`. New successful receipt writers set NULL atomically with the external receipt and status. For `record_candidate_action_outcome`, only use NULL if its body equals that same receipt; otherwise store the attempt-local body. `result_digest`, provider response and target binding remain solely in the external receipt. No new authorization or reconciliation policy is needed.

The target DDL delta is limited to the `candidate_action_attempts` payload type condition: old `json_type(payload_json, path_to_result_json) IS 'text'`; new `(json_type(...) IS 'text' OR json_type(...) IS 'null')`. Its positional field count, generated `result_json` projection, record code, indexes and FKs remain unchanged. The explicit inverse projection is equivalent to:

```sql
SELECT CASE WHEN a.status='verified' AND a.result_json IS NULL
            THEN r.provider_result_json ELSE a.result_json END AS result_json
FROM actions AS a
LEFT JOIN actions AS r ON r.record_type='external_action_results'
                      AND r.external_action_key=a.external_action_key
WHERE a.record_type='candidate_action_attempts';
```

Readers needing the attempt's original result can use an explicit owned projection: `CASE WHEN attempt.status='verified' AND attempt.result_json IS NULL THEN receipt.provider_result_json ELSE attempt.result_json END AS result_json`, with the receipt joined by `external_action_key`. Current consumers include `SystemExecutor.execute` and handlers in `app/system_action_handlers.py` for uncertain/failed reconciliation, `ReviewedCandidateStoreMixin.get_prior_candidate_action_attempt`/`list_candidate_action_attempts`, `list_verified_candidate_actions`, and display/history paths. The nonverified branches keep reading attempt-owned bytes. `get_candidate_external_action`, `agent_orchestrator`, `worker`, and `attempt_what_happened` already read the external receipt directly. Do not use a blanket truthy fallback: `{}` and NULL have different ownership meanings, and an absent receipt is an integrity failure for a NULL verified attempt.

Inverse in the same versioned schema release projects every current attempt. If `status='verified' AND result_json IS NULL`, reconstruct old `result_json` from the current matching `external_action_results.provider_result_json`; otherwise copy the current attempt value byte-exactly. This reconstructs newly inserted successful attempts as well as preexisting duplicates; it preserves the one live distinct `{}` and all failure/uncertainty proof. Preserve `legacy_key`, physical `id`, `execution_id`, `action_index`, external key, timestamps and receipt `first_agent_run_id`. Test same-key reuse in later revisions without deleting the earlier external result, ambiguous-to-sent receipt correction, action completion and error recovery, a divergent verified `{}` source row, forward/new-write/inverse, FK and allocator water. The relevant current tests are `tests/test_action_receipt_schema_release.py`, `tests/test_action_receipt_callers.py`, `tests/test_reviewed_candidate_store.py`, `tests/test_system_executor.py`, `tests/test_history_actions.py`, and `tests/test_dingtalk_delivery_repair.py`.

## A3: one reviewed plan version owns execution state

The source is **not** a one-row candidate/execution pair in every case. The live read-only inventory found 1,027 `review_candidates`, 1,017 independent `candidate_reviews`, 326 `candidate_executions`, and 316 `candidate_action_attempts`; 701 candidates have no execution. Among the 326 pairs, zero candidate/execution **physical** Actions IDs coincide, and only one pair's integer public IDs coincide. Selection and review history remain distinct facts. A3 can eliminate the second lifecycle owner only if it preserves the execution identity required by old links, attempt FKs and the paired inverse.

Proposed minimal target for this slice: keep the candidate's existing physical Actions row as the authoritative **plan-version** row and add the following optional execution facts to its target layout. Each name on the right is an explicit source mapping, not a new business inference:

| Target plan-version field | Exact old source |
|---|---|
| `execution_public_id` | `candidate_executions.legacy_key` (old public `id`) |
| `execution_review_id` | `candidate_executions.review_id` physical FK |
| `execution_selection_id` | `candidate_executions.selection_id` physical FK, nullable |
| `execution_status` | `candidate_executions.status` |
| `execution_lease_owner`, `execution_lease_expires_at` | same-named `candidate_executions` fields |
| `execution_result_json` | `candidate_executions.result_json` |
| `execution_created_at`, `execution_updated_at` | `candidate_executions.created_at`, `.updated_at` |

`review_candidates`' existing `created_at`, `invalidated_at`, and `invalidation_reason` retain their original candidate meanings. A nullable execution block means no execution has ever been created; do not synthesize a terminal state from the candidate or review. Candidate review records keep their own `id`, `audit_run_id`, decision, digest, result and timestamp. A candidate can have several reviews; `execution_review_id` pins the adopted one. Selection remains pinned by its stored `selection_id` and immutable `option_key` from A1.

For preexisting execution **physical** identity, transform its row at the same `actions.id` into an immutable `candidate_execution_alias` with just `legacy_key` (old execution public ID), `candidate_id` (plan physical FK), and no status, lease, result or timestamps. This is a technical identity alias, not another lifecycle. The old `candidate_action_attempts.execution_id` physical FK can point to that alias until the common step/attempt refactor; runtime resolves alias to its plan. If the final target retires aliases too, it needs an equally exact immutable ID reservation map plus a cross-table allocator guard; a mere inverse metadata list cannot prevent SQLite from reusing a deleted physical ID. Prefer the alias for the first implementable A3 release. When a previously unexecuted candidate is claimed, create one alias with the old per-type public-ID allocator and fill the plan's execution block in the same transaction. This also gives a current source from which the inverse can reconstruct *newly created* executions.

Target DDL shape, expressed as generator deltas rather than hand-edited SQLite text: the existing compiler excludes foreign keys from JSONB payloads. Therefore `execution_review_id` and `execution_selection_id` are **nullable physical typed foreign key columns**, mapped directly from the old execution's `review_id` and `selection_id`; their referenced candidate review and selection physical IDs remain unchanged. Only the other seven mapped values append to the `review_candidates` JSONB layout. A complete execution requires its public ID, review FK, status, lease values, result and timestamps; selection FK remains nullable as in the source. With no execution, all nine values are null. Enforce this all-or-none condition and the same-candidate review/selection binding in the target declaration. `candidate_execution_alias` preserves the old execution row's physical ID and `legacy_key`, a unique candidate FK/index, and no result/status generated columns. Exactly one alias must correspond to a complete plan execution block, with matching public ID; no block permits no alias. `candidate_action_attempts.execution_id` FK is retargeted to the alias type while its public `execution_id` projection remains the old integer. Keep source code/type codes for the frozen inverse and append a new alias discriminator instead of renumbering `ACTION_RECORD_TYPES`. `claim_candidate_execution`, `renew_candidate_execution_claim`, `_leased_execution`, `_owned_execution`, `finish_candidate_execution`, and `get_candidate_execution` in `reviewed_candidate_store.py` become plan-row state operations with an old-shaped projection for callers. That projection returns the alias's old physical/public execution identity, never the candidate ID; this preserves the joins in `get_verified_action_source` and verified-action History. `system_executor`, `agent_orchestrator`, `worker`, Store, History, quality gate and attempt detail must use that projection, never issue a second state write to an alias. `candidate_action_attempts` and `external_action_results` remain per-effect attempt and external-result owners after A2.

Forward copy conversion reads each exact candidate/execution pair, keeps the candidate physical ID, moves execution values into the candidate payload, and rewrites the execution row *at its existing physical ID* to the alias. Existing attempt FKs remain valid. Verify at most one execution per candidate, exact `review_id`/selection bindings, source counts/projections, public IDs, unique candidate ownership and FK findings before commit. Inverse uses current plan block plus alias to rebuild the frozen `candidate_executions` row at that alias physical ID, including executions created after forward migration. If an alias exists without a complete plan block, or a plan block lacks its alias, refuse inverse. An absent block produces no execution row. Do not store a pre-migration row-body snapshot. Tests need candidates with 0 and 1 executions, multiple reviews, selected and unselected plans, renewed lease, terminal result, superseded generation, new post-migration execution and attempt, exact old/public/physical IDs, allocator continuation and forward/inverse from both historical source variants.

## B2: one plan/step/attempt path for email effects

This slice is larger than deleting the last result fields on `email_actions`. Current live counts were 10,527 `email_action_plans`, 10,949 `email_actions`, and 13,006 `email_action_attempts`. Of the 10,907 direct actions with at least one attempt, all had `attempt_count == count(attempts)` and their latest attempt exactly matched the action row's `status`, `provider_operation`, `provider_target`, `provider_result_id`, `error`, `started_at`, and `finished_at`. Forty-two pending direct actions had no attempts. Source schema enforces attempt count with `trg_actions_email_attempt_count_*`; preserve its real count/ordering semantics while retiring the seven latest-result copies. All these counts are live aggregates, not fixture assumptions.

The normalized target should have one **plan-version**, **effect step**, **effect attempt**, and **external result** mechanism for reviewed Consumer and deterministic email actions. These are structural record families, not a requirement to make email decisions pretend to be Consumer runs. Append target `_kind` codes, preserving old codes for the frozen source/inverse. Target plan-version origin is either the current reviewed candidate or the current `email_action_plans` row; target step origin is a reviewed action in the bound proposal/selected option or one `email_actions`, reply claim or unsubscribe claim; target attempt origin is one `candidate_action_attempts` or `email_action_attempts` row. The origin discriminator and target `*_public_id` aliases encode exact existing source identity; they do not claim a new business fact. When a source Actions row has a target counterpart, reuse its physical `actions.id` and `legacy_key`, rather than allocating a replacement row. A reviewed plan with no selected executable option gets no effect steps. For email, an immutable plan may list reply/unsubscribe as well as direct actions; those effects become steps only under the exact existing binding and claim semantics.

The runtime conversion sequence is: (1) versioned plan/step/attempt target DDL with origin-specific constraints, indexes and projections; (2) transactional current-fact copy preserving Actions physical IDs and the independent email attempt/step public IDs; (3) move `EmailStore._persist_action_plan`, `_ensure_direct_action_rows`, `claim_next_direct_action`, `claim_direct_action`, `append_action_attempt`, `complete_direct_action_attempt`, stale recovery, retry and result readers to shared plan/step/attempt writer methods; (4) route `DeterministicEmailActionExecutor`, `email_action_reconcile`, reply and unsubscribe handlers through the same claim/result methods while keeping their typed provider verifiers and evidence; (5) remove old lifecycle generated columns, indexes, triggers, writers and allocator paths only after all live readers/Console routes use target projections. Do not call a deterministic provider effect a Consumer Agent execution, add an Audit run, or alter an immutable plan's `authorization_snapshot_json`/`config_version` during this move. The inverse reconstructs old plan/action/attempt/claim rows from current version, step, attempt and specialized evidence records, including writes after forward conversion; it fails if an old-only unique field has no mapped current owner. Tests must include reclassification after an old action, all six direct provider operations, retry/stale recovery, reply and unsubscribe uncertain readback, exact receipt/no replay, source no-op/skipped outcomes, public/physical identities and empty-family historical fixtures.

The minimum target constraints and FK translations are as important as the column copy. A common plan-version row must retain unique `(classification_id,action_plan_version)` for Email, unique Consumer `consumer_run_id`, and the original public `action_plan_id`/candidate ID. A common step row needs origin-scoped unique `(action_plan_id,action_type)` for direct email, unique `action_id`, unique reply `outgoing_message_id`, and unique email `action_identity` within each reply/unsubscribe origin. A common attempt row needs origin-scoped unique `(action_id,attempt_number)` for direct email and `(execution_alias_id,action_index)` for the reviewed action's current attempt. Claim owner/lease fields belong to the step; terminal provider result fields belong to the attempt or an external receipt. Repoint `email_feedback_requests.expected_current_action_plan_id` and `.resulting_action_plan_id`, `emails.class_current_action_plan_id`, `email_direct_retry_requests.action_id`, and reply/unsubscribe receipt/effect/step/continuation parent references to the corresponding target plan/step *before* dropping old kind checks. The inverse restores those exact old FKs, source unique indexes and email attempt/step allocator waters from the current rows.

For implementation, make the source-to-target copy finite and source-kind explicit, rather than an untyped bag. The target `action_steps` payload variants are: direct email = (`action_id`,`action_plan_id`,`classification_id`,`account_id`,`action_type`,`parameters_json`,`config_version`,`status`,`next_attempt_at`,`created_at`,`updated_at`, plus `started_at` only while processing); reply claim = every field in `EMAIL_FIELDS['email_reply_dispatch_claims']`; unsubscribe claim = every field in `EMAIL_FIELDS['email_unsubscribe_claims']`; reviewed effect = bound plan ID, selected action index and the exact `ProposedAction` fields already held in candidate JSON. The target `action_attempts` variants are the two complete source tuples in `EMAIL_FIELDS['email_action_attempts']` and `SOURCE_COLUMNS['candidate_action_attempts']`, with A2's explicit NULL receipt-ownership rule. Once each variant is declared, exclude only the proven duplicate terminal direct-action fields from the step payload, deriving them in the old-shaped projection. The specialized evidence kinds in the preceding table retain their complete current `EMAIL_FIELDS[kind]` tuples unless an exact field-by-field rehome is proven in a copy and inverse test. This avoids a half-migrated target that stores a generic status while retaining a second email-only lifecycle writer.
