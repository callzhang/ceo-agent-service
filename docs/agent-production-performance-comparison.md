# Agent优化：已有生产trajectory耗时与token比较

日期：2026-10-25（America/Los_Angeles）。本报告只读分析已有生产数据库及CLI原生JSONL；未运行新测试、未调用模型、未重放任务、未操作业务文档。本节比较窗口明确使用UTC，避免与报告本地日期混淆。

## 结论

**可比的钉钉Consumer冷启动生产样本有实际下降：48对输入规模匹配样本，Agent运行耗时中位数51→35秒（-31.37%），累计输入token341,099→269,719.5（-20.93%），非缓存输入83,989.5→60,840（-27.56%）。** 这是历史生产的观测结果，支持“这一批运行实际更快且用量更少”；不是严格A/B，不证明整轮优化的因果收益，也不等于整项任务端到端提速31%。

同窗口Audit的匹配样本耗时也下降10.81%，但累计输入token反而增加10.24%。说明环境、输出长短和同期其他变更都在变化，不能把Consumer全部提速归因于prompt精简。最新PR327移除文档内容核验尚无自然文档写入样本，不量化其收益。

## 1. 数据与可比范围

读取生产runtime_attempts中2026-10-06至本次提取截止的Codex Consumer/Audit与Meeting记录，共4,438个attempt；1,914个有可恢复原生范围，其中1,400个已完成且有可用token计数。缺失文件或计数不按零处理。各日期、模型、工作负载覆盖率保存在结果JSON。

原始按需指令于10月8日、Meeting精简于10月18日发布。更早原生文件大多已不可定位：10月6–9日579条已完成Consumer/Audit记录没有可读JSONL；Meeting发布前窗口也无可用token。因此不能声称还原了“最初优化前→全部优化后”的完整token比较。

选择能够核对实际输入变化的PR245（Consumer重复schema精简）窗口：合并时间2026-10-22 12:12:35 UTC。前窗为10月21日00:00至该时刻，后窗至10月25日00:00 UTC。合并时间不冒充部署时间：实际入选Consumer前窗均包含`Pydantic Wire Contract`，后窗均不包含，按真实Developer输入确认变化。

限定同为Codex本机OAuth、GPT-6 Luna、high、fresh、已完成的普通钉钉Consumer；剔除OA、定时报表、微信、其他模型和resume。该分类来自任务当前输入的channel/oa_url，属于粗任务分类，不保证两条业务问题难度相同。未匹配样本为前50、后99。原生turn_context独立确认模型与effort，不只使用数据库配置值。

在结果变量不参与选择的前提下，按前窗时间顺序，为每条记录选择后窗用户输入字符数对数距离最近的一条，不放回；字符比限定0.8–1.25，得到48对。输入规模取首个模型响应前、bootstrap之后的用户消息字符合计，不含工具读回或完整历史上下文；不是全部业务事实长度。两组该字符数中位数17,910→17,949.5，仅+0.22%。样本配对ID和各段摘要已保存，不存业务原文。

## 2. Consumer：匹配样本的实际数字

以下均为各组中位数，不是同一请求的差值平均。累计输入包含该Agent turn内多次模型请求，重复上下文计入实际用量。

| 指标 | 精简前，48项 | 精简后，48项 | 变化 |
| --- | ---: | ---: | ---: |
| 服务Agent运行耗时（秒） | 51.0 | 35.0 | -31.37% |
| 原生turn耗时（秒） | 41.0 | 27.0 | -34.07% |
| 累计输入token（含缓存） | 341,099.0 | 269,719.5 | -20.93% |
| 其中缓存输入token | 252,032.0 | 204,160.0 | -18.99% |
| 非缓存输入token | 83,989.5 | 60,840.0 | -27.56% |
| 输出token（含推理） | 2,378.0 | 1,876.5 | -21.09% |
| 输入+输出总token | 343,048.5 | 272,314.0 | -20.62% |
| 首轮模型请求输入token | 32,915.5 | 31,533.5 | -4.20% |
| 工具调用次数 | 6.0 | 5.0 | -16.67% |

服务耗时P90为277→62秒；原生turn耗时中位数40.97→27.01秒。长尾受工具数和业务难度影响大，不能把P90差值归因于单个代码变更。

未做输入匹配的前50/后99样本，服务耗时中位数50.5→38秒（-24.75%），累计输入312,598→279,910（-10.46%），方向相同。这是匹配敏感性检查，不是第二组独立实验。

关键解释：Developer文本中位数45,619→33,037字符（-27.58%），但首轮请求输入token只下降4.20%；模型还接收工具schema、原生上下文及其他说明。累计输入下降20.93%还伴随工具调用6→5、输出token下降21.09%，因此不能将全部token/耗时变化说成初始prompt缩减的直接效果。

同模型/路线/effort/fresh/粗任务类型、同输入规模方法得到92对Audit样本。

| 指标，中位数 | 前窗 | 后窗 | 变化 |
| --- | ---: | ---: | ---: |
| 服务Agent运行耗时 | 37秒 | 33秒 | -10.81% |
| 累计输入token | 292,429.5 | 322,363.5 | +10.24% |
| 非缓存输入token | 63,126.5 | 71,270 | +12.90% |
| 输出token | 2,080 | 1,685.5 | -18.97% |
| 首轮请求输入token | 34,195.5 | 40,855 | +19.47% |

Audit并未享受同一个Consumer schema删除，且同期Developer中位数42,164→70,177字符；其他上下文/原生输出变更存在。因此它只是证明“token和耗时不总是同方向”的同期参照，不能据此做严格差分来计算prompt的净因果收益。

## 4. Meeting与文档写入：不能补造缺失结论

Meeting同为gpt-5.6-luna/Codex OAuth：发布前窗口10月15日至10月18日09:11:50 UTC，30项已完成运行；后窗至10月21日04:00，35项。服务耗时中位数28.5→26秒，约-8.77%。但前窗原生token记录为0/30可用，后窗35/35可用；前后会议材料规模、模型实际effort和内容难度不能对齐。因此只作未调整的元数据描述，不认定Meeting精简导致提速，也不估算其token节省。

PR327于2026-10-26 03:47 UTC发布。提取时该点之后42个可读原生attempt中没有具名`consumer_document_write`调用；前述有限完整自然回读也没有相关样本。这里不声称具名工具扫描能覆盖所有可能脚本路径，不声称文档重复覆盖24→0，也不把工具删去一步换算成秒数。

## 5. 计量方法与局限

- 服务耗时：同一个runtime attempt的finished_at−started_at，包含CLI启动/工具等待等；不含领取前排队，不覆盖整项任务多次反馈/发送的端到端耗时。原生耗时另以task_started/task_complete计算。
- token：只读该attempt的准确原生行范围；末尾累计用量减去范围之前最后一次累计用量。冷启动从0开始，续会话不重复计历史成本。忽略同一请求的token_usage_record副本；counter重置、缺失或不完整范围不编造用量。
- cached_input_tokens是input_tokens子集；reasoning_output_tokens是output_tokens子集，均不再加一次。非缓存输入=输入−缓存输入。token为CLI报告值，不等同OAuth实际账单，不能换算美元。
- 只对完成且有原生计数的运行做主比较，存在完成样本选择偏差。未匹配普通钉钉fresh元数据另有Consumer前窗21个failed、后窗0个failed；Audit前窗14个failed/3个superseded、后窗1个failed。不是相同故障条件的成功率实验，不把它解释为优化提升成功率。失败状态和缺失覆盖保留在JSON。
- 未固定事实正文、完整工具目录、模型服务负载、网络、Skill正文、会话初始历史与同期代码变更；不是随机实验。两窗口初始消息规模相近不能替代完整业务复杂度匹配。未评估这些生产输出的业务质量变化。

**可交付判断：已观察到一组经过基本匹配的生产Consumer运行更快、token更少；尚不能量化整轮优化的独立提速、完整任务耗时或费用收益。** 这比只有字符减少更进一步，但不把观察性关联写成确定因果。
