# Task 6B Dashboard failure diagnosis

## Finding

Both reported failures reproduce from the saved Task 6B final backup, opened read-only. They are current Action schema/reader contract mismatches. The acceptance launcher did not cause them: the queue failure reproduces through the registered HTTP route with a read-only Store stub and the same backup, without loading `create_audit_app`, starting workers, or invoking a provider.

The `/api/console/dashboard/queues` route returns 500 because its auxiliary Email action query still compiles the retired `email_actions` projection. The exact traceback reaches `dashboard_queues` → `read_dashboard_queues` → `_append_auxiliary_queues`, then fails at `db.execute(sql)` with `sqlite3.OperationalError: no such column: a.email_action_type` (`app/web_api/dashboard.py:412-421, 248, 316-335`). The projection from `email_action_projection("email_actions")` selects `a.email_action_type` and filters `record_type='email_actions'` (`app/shared_action_definitions.py:82-108`). The final backup declares Store version `2026-10-21.1`, Email schema 53; its `actions` table has `action_operation`, `action_status`, `action_action_plan_id`, and `action_classification_id`, but no `email_action_type`. The current email reader already defines this unified shape in `app/email_store.py` (`DIRECT_EMAIL_ACTION_SQL`) and `app/email_publication_sources.py:44-47`. The queue route's legacy projection is the stale caller.

The status validation failure is the same ID-contract gap surfaced on Attention. A read-only call to `_queue_attention_rows` against the final backup returns rows 2 and 3 as category `Email action`, with integer IDs `134250` and `134221`. `app/audit_web.py:3741-3749` explicitly writes `int(row["id"])`; `AttentionRow.id` is declared `str` at `app/web_api/status.py:163-173`, and `/api/console/status` validates the enclosing `WorkerStatus` at `app/web_api/registration.py:680-685`. `AttentionRow.model_validate` rejects these exact rows. The pinned old source's Email action Attention producer stringifies the ID (`/private/tmp/ceo-action-entity-validation.8rUAvK/old-code-897227b/app/audit_web.py:3739-3749`), confirming that integer output entered on the migrated current-source path. On this final backup, the Reply-attempt producer is not the failing source: `AutoReplyStore.list_current_unresolved_problem_attempt_summaries` returns string IDs, consistent with the old source (`app/store.py:21006+`).

## Attribution and evidence boundary

The Dashboard handler is inherited code, but the failing schema is the accepted Task 6B target (`store_schema_version=2026-10-21.1`, Email 53), with the old Email action discriminator absent. The source declarations distinguish the current generic Action projection from the retired Email action layout. That makes this a migration-affected reader compatibility defect exposed by the acceptance candidate, not a copied-server-only failure. The original pinned 897 code and current candidate represent different schema sides; this diagnosis does not claim an independent live production failure or a successful old-baseline HTTP request.

The report's task-owned directory retains `serve_acceptance.py`, the fake-call JSONL and final SQLite backup, but no Uvicorn access/error log. I reproduced the exact queue exception through `TestClient` at `/api/console/dashboard/queues`; the traceback ends at `dashboard.py:335` with the SQLite error above. The status producer was read against the same backup in `mode=ro` / `query_only=on`; the affected Attention IDs were then validated against the actual `AttentionRow` model. The final backup's SHA-256 remains the value recorded by Task 6B: `7732ba9cac36047b19d497aeb5ad1959995e9f2d034119ccc9983920f21abdc5`. No database writes, app edits, service access, provider calls, or broad scans were made.

## Minimal repair and regression proposal

1. Update the Dashboard's Email queue caller to read current generic Email actions through the existing current Action projection (`DIRECT_EMAIL_ACTION_SQL` plus the current classification projection and its existing retry predicate). Keep the route's queue contract and filtering unchanged. Add a focused route regression against the Store `2026-10-21.1` declaration that fails with the present `email_action_type` reference and returns 200 with current queued/retryable Email actions after repair.
2. Serialize Email action Attention IDs as strings at the row producer, matching `AttentionRow.id` and the pinned baseline public output. Add a focused regression with an integer public action ID that asserts the returned field is a string and that `AttentionRow`/`WorkerStatus` validation succeeds. Keep numeric IDs for database joins and URL construction where those consumers require them.

No application code or test files were changed, and no test suite was run. The only active check was the focused read-only route/model reproduction described above. This proposes no runtime policy, retry, or authorization change.
