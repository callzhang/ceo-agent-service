# Task2C Reply creator implementation report

Status: implemented and locally verified on the unpublished Task/Run Phase2 worktree. Implementation commit: `864459462` (`Convert reply task creator to native Task owners`).

## Converted closure

The existing `AutoReplyStore` class and its transaction boundaries remain. The creator path now calls `task_entity_storage.create_task`, `append_task_input`, `bind_current_input`, `get_task_with_inputs`, and `associate_business_key` against the assembled target. Converted methods are `_append_reply_input_snapshot`, `_ensure_business_reply_task`, `enqueue_reply_task`, `ensure_reply_task`, `ensure_reply_tasks`, `ensure_authorized_email_reply_tasks`, `_ensure_reply_tasks_in_transaction`, and `get_reply_task_for_execution`. `_reply_task_from_native` projects the canonical Task plus its bound current input for creator returns or its bound claimed input for execution lookup; it does not decode old and new schemas together. Shared `REPLY_TASK_*` source projections remain for caller groups that have not moved.

## Preserved behavior and evidence

- Triple `(channel, conversation_id, trigger_message_id)` dedupe returns the original owner and its current-input projection. `enqueue_reply_task` reports whether the immutable input was newly inserted.
- Input identity remains the full four-part key including `input_revision_key`. Same-owner reuse compares all existing source fields, and owner or byte conflicts preserve `ReplyTaskIdentityConflict`.
- A business key reuses its Task. New messages append immutable inputs and advance the current binding/version; the claimed input and a nonterminal execution generation stay fixed. A new input on a `done` or `failed` Task resets its queue state, retry count, lock, error, availability, and generation.
- OA provisional-key refinement updates `business_object_key` on every existing input of the owner and replaces the provisional TaskBusinessKey relation in the same transaction, matching the predecessor. Trigger text, message JSON, provenance, and current/claimed pointers remain unchanged; an already-claimed execution therefore retains its old message while observing the refined key. Multiple keys remain rows in `task_business_keys`.
- The Task parameters contain only `force_new_decision`, `manual_rerun_attempt_id`, `manual_rerun_revision_key`, and `recovery_code`. Reply context fields come from the bound current or claimed TaskInput; numeric input versions remain numeric. `_reply_task_from_native` passes business values into the existing `ReplyTask` model without eager string/integer coercions, preserving source Pydantic parsing for SQLite BLOB/REAL values.
- Authorized email batching reads current classification/message ownership from the assembled Email tables and rejects a stale plan before inserting reply Tasks.

## DTO parsing parity correction (Fix 2)

The native `ReplyTask` projection now sends stored business values to the same existing Pydantic model without added `str()` / `int()` coercions. The actual source reader converts valid UTF-8 BLOB trigger text and message JSON into readable strings through Pydantic, and rejects fractional `attempts=1.25` with `ValidationError`. The previous native projection instead surfaced `b'typed source text'` and silently reduced the attempt count to `1`. Both differences are corrected without changing TaskInput bytes or migration behavior. Existing boolean and numeric input-version conversions, native identifier normalization, and compacted-input hydration are retained.

Paired current/claimed tests perform actual source writes and source DTO reads, migrate with `capture_task_entities` / `migrate_task_entities`, then compare native projections and exception behavior. They verify BLOB body/JSON bytes and SQLite types on both sides of migration, current and claimed DTO selection, and source public input IDs separately from native physical IDs.
