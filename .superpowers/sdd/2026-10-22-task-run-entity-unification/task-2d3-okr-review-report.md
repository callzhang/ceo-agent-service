# Task2D3 OKR review Task/Run/runtime attempt integration

## Scope and result

The OKR review request producer now uses the native `okr_review` Task as its queue and identity owner. The existing dedupe key remains `(conversation_id, trigger_message_id)`. Only failed duplicates reopen; they refresh the admitted source JSON, status, error, session and update time while preserving creation time and the existing request data. Claim remains ordered by native Task ID and only changes pending to processing. Recovery reads native Tasks, applies the existing processing-age and stale session-lock conditions, clears the exact `okr_review:<Task ID>` lock owner, and returns the pre-reset DTO. Done/failed and item writes address the same canonical Task ID; item rows remain in `okr_review_items` and no TaskResult or aggregate payload was added.

`process_okr_review_request` retains CLI → normalization/validation → professional Run creation → domain item writes → Task done/render order. A failed or invalid result creates no professional Run. `StructuredAgentRun` now carries the `attempt_id` returned by routed execution. The producer binds that exact ID after Run creation using the native attempt CAS primitive, after verifying the completed structured attempt, canonical request Task key, OKR Task, Run Task owner and `okr_review_runs` provenance. It does not look up an attempt by latest ID, session or transcript range. Invalid structured output leaves its completed attempt parentless. The native Run reader follows only the exact `runtime_attempts.parent_id` edge, plus `structured` and canonical Task-key checks. Historical standalone source Run session/range facts retain their prior exact fallback. A Run can be read by native Run ID and provenance when its Task row is absent; no old request ID is inferred.

Task-absent lifecycle facts remain `NULL` on the assembled Task, and source-absent Run fields (status, error, role and execution generation) remain `NULL`. Weekly OKR analysis remains a separate Task kind and was not changed. No constructor activation, model/provider call, production checkout, `main`, push, deploy or full-suite run occurred.

## Native Run-reader Fix1 review follow-up

The independent review found that an invalid `parent_id` edge could be hidden by filtering for the expected workload before edge detection, allowing fallback to the Run's stored session/range. The reader now inspects every attempt attached to the native Run first. If any edge exists, only exactly one completed `structured` attempt with the Run Task's canonical key is accepted; wrong kind/key, failed status, or multiple edges returns unavailable and never reaches historical fallback. When no parent edge exists, the reader preserves the prior strict source-fact behavior: an exact parentless structured Task-key/session/range attempt is usable; an attempt for that Task without an exact unbound match blocks Run-trace fallback, including an attempt parented to another Run; unrelated Tasks' attempts do not block a Run's own stored session/range. A NULL Task ID does not create a workload key and the Run's own session/range remains directly readable. No source ID mapping or body persistence was introduced.
